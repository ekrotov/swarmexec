MCP server for AI assistants_

Read-only Swarm access for an AI assistant, per service, by label.

mcp — let an AI assistant inspect the swarm

swarmexec mcp is a Model Context Protocol server on stdin/stdout. An AI assistant such as Claude Code can then look at the swarm through the same two channels every other command uses — the manager API and the node agents — on any Docker context, ssh:// included. It reads status, tasks, logs and resource usage, diffs and checks stack files, and, where you allow it, runs a single non-interactive command in a container. It changes nothing.

claude mcp add swarmexec -- swarmexec mcp

See the recipe: let Claude inspect your swarm.

Every tool takes an optional context argument; without it the server uses the context it was started with (--context, DOCKER_CONTEXT, DOCKER_HOST, docker's current context). Connections are kept per context for the session, as the TUI does on a context switch.

Only the contexts you allow. The assistant gets the context the server was started with, plus those named with --contexts — nothing else. Every other context on the workstation, production included, does not exist for it: contexts_list leaves it out, name and address, and naming it answers unknown docker context, exactly like a name that does not exist.

swarmexec mcp --context staging --contexts lab,test

Access: service labels

What the assistant may see is decided per service by service labels — in a compose file, deploy.labels, the way Traefik is configured in Swarm mode. Nothing is visible by default.

# compose file: deploy.labels, not the container labels services: api: image: registry.example.com/api:1.4 deploy: labels: swarmexec.mcp.enable: "true" # the service exists for the assistant swarmexec.mcp.logs: "true" # it may read the logs swarmexec.mcp.exec: "true" # it may run a command in a container
  • Opt-in. A service without swarmexec.mcp.enable does not exist for the assistant. --default read makes unlabelled services visible (status, tasks, inspect, stats) — never their logs, never exec.
  • An explicit "false" always wins, over the default and over the other labels. A value that is neither true nor false counts as false.
  • An unknown key under swarmexec.mcp. — a typo such as swarmexec.mcp.exce — grants nothing and is written to the log file as a warning; so is an access label set as a container label.
  • A service it may not see is indistinguishable from one that does not exist: the same no such service, absent from every list, count and stack diff. A visible service without logs or exec answers a plain not permitted.

Security notes

  • The labels are invisible to the assistant. They are removed from everything it receives — inspect, lists, task details, stack diffs and checks, error messages — from service and container labels alike, and every result passes one last filter on the way out. It can infer its access from what works, which is accepted.
  • They cannot be changed through MCP. There are no write tools. Any future one has to pass a guard that compares the service before and after the change and refuses if an access label would be added, changed or removed.
  • A service that can reach the Docker daemon is never exec'd into, whatever its labels say: the Docker socket bound in (the security scan's rule), a bind of the directory it lives in, the Windows pipe, and the swarmexec agent itself. Through the socket, anything could relabel any service. The agent's own authorization policy still applies on top.
  • Prompt injection. Log lines and command output are written by the applications. Anyone who can get text into a log can put instructions in front of the assistant; treat logs and exec as access for whoever writes to those logs, too.
  • Data goes to the model provider. Whatever a tool returns is sent to the assistant's model. Environment values whose names look like credentials (the scan's secret in environment variable rule) are masked, secrets and configs are listed by name only, and every result is capped in size and says when it was cut — but log lines and command output are passed as they are.
  • Masking is cosmetic once exec is granted. A command run in the container can print its environment and read its mounted secrets (env, cat /run/secrets/…), so the masking in inspect, diff and check results protects nothing on a service with swarmexec.mcp.exec. Grant exec only where the assistant — and the model provider — may see everything the container sees.
  • Audit. The operator reported to the agents is <you>+mcp, so the audit log shows which actions the assistant took. With mTLS the certificate's CN decides the identity; give the assistant a client certificate of its own to tell it apart there.
  • ssh cannot ask. stdin and stdout carry the protocol, so ssh runs in batch mode: a passphrase-protected key must be loaded in ssh-agent, and a host key must already be in known_hosts. The error says which. Logging goes to the log file, never to stdout.
  • An assistant working in the repository can read the labels straight from the compose file — they are hidden from the server's answers, not secret.
