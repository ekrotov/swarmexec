Authentication & policy_

Who may talk to the agents, and what they may do.

On this page

  1. Authentication
  2. Authorization policy

Authentication

The client authenticates to the agent in one of two modes.

Mode A — mutual TLS (default)

Set ca, cert and key (all three required). The client verifies the agent against your CA and presents its certificate; the agent authorises and audits you by the certificate's CN. This is the default and the recommended posture.

$ swarmexec --ca ca.crt --cert me.crt --key me.key ps

Mode B — self-signed agent + shared secret

Simpler to run (one secret, no PKI) — this is what init sets up. Set agent_secret (or agent_secret_file), and either a ca to verify the agent or insecure: true to skip verification. A client cert is optional (but cert and key must be set together or both empty). Your audit identity is the operator value (default: your OS username).

$ swarmexec --agent-secret "$SECRET" --insecure ps
insecure skips the agent's server-certificate check. It does not put the secret at risk: the client never sends it, only a proof computed from the secret and the certificate of the connection it travels on, so a server you did not verify receives nothing that works against a real agent. What remains is that the agent is not authenticated to you — whoever answers can read what that session sends them. Prefer a ca on any network you do not trust, and keep the secret out of your shell history (use agent_secret_file or the config file).

Upgrading to v1.17.3 — update the agents first

A v1.17.3 client cannot authenticate to an older agent. It sends only the connection-bound proof, and agents before v1.17.3 do not recognise that form — they answer invalid or missing agent secret even though your secret is correct. Update them first:
$ swarmexec init --force
While a fleet is mixed, legacy_secret: true in the client config also sends the raw secret, with the exposure described above. Remove it once the agents are current, then re-run swarmexec init --force --allow-legacy-secret=false so no client can put the credential on the wire by accident.

Authorization policy

By default an agent allows every request that passed authentication. A rule file narrows that: which actions (container.list, container.events, exec, logs, portforward, stats.read, image.list, image.prune, image.prune.all, volume.list, volume.create, volume.remove, reclaim.read, container.prune, buildcache.prune, network.prune, volume.prune; globs like volume.* work) for which services, ports, exec users and — with client certificates only — operator identities. Within a rule every condition must hold; the first rule that matches decides, and default (required) covers the rest. The agent's version probe is not an action and is never refused by a policy, so doctor can still report an agent's version to a denied identity.

# policy.yaml — the first rule that matches decides; "default" when none does default: allow rules: - deny: [image.prune.all] reason: no sweeping prune on production - deny: [portforward] ports: [5432, 3306] reason: no forwards to the databases - deny: [exec] users: [root, "0", "0:0"] - deny: ["volume.*"] services: ["prod_*"]
swarmexec init --force --policy-file policy.yaml

A refusal reaches the client as permission denied with the rule and its reason, and the same text lands in the audit log. init checks the file before deploying anything, and the agent refuses to start on one it cannot read: an unknown action, a misspelt key or a broken pattern is an error, never a rule that silently matches nothing. Rules on identities are refused while the agents use a shared secret without client certificates — the identity is then whatever the client claims. An exec without -u runs as the image's user, which the agent cannot see; users: [""] matches it. Change the file and re-run init --force; run it without the flag to drop the policy.

What this is not. A policy prevents accidents and records intent — no sweeping prune on production, no forward onto the database. It is not access control: everything swarmexec changes on services, secrets, networks and stacks goes to the swarm manager with your own Docker credentials and never passes an agent, and whoever holds those can deploy a service that is root on every node. Restrict the Docker credentials for that.
