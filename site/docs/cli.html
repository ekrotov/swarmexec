swarmexec exec

Exec into a container running anywhere in the swarm

swarmexec exec [flags] <service|service.slot|task-id|container-id> [-- <cmd> [args...]]

Open a shell, or run a command, in a container on whatever node of the swarm it runs — the docker exec experience, without ssh to that node.

The target is one of:

service        the service's running task, e.g. web
service.slot   one replica, e.g. web.2
task-id        a Swarm task ID
container-id   a container ID prefix (--node names its node, or the running
               tasks are scanned for it)

A service with several running replicas is ambiguous: on a terminal you are asked to pick one from a numbered list; without one the candidates are printed and nothing runs. Name a slot to skip the question.

With no command it opens /bin/sh, with a TTY when stdin is a terminal. The remote command's exit code is passed through.

Examples

swarmexec exec web -- sh swarmexec exec web.2 -- cat /etc/hostname swarmexec exec -u root -w /app web -- ls -la
FlagDefaultDescription
--connect-timeout duration10stimeout for connecting to the agent
-e, --env stringArray—set environment variables (KEY=VALUE, repeatable)
--node string—node hint/override for container-id targets
-i, --stdintruekeep stdin open
-t, --ttyfalseallocate a TTY (default: auto — true iff stdin is a terminal and no command)
-u, --user string—username or UID (e.g. 1000:1000)
-w, --workdir string—working directory inside the container

Also takes the global flags and the connection flags.

swarmexec logs

Stream logs of one or more containers, services or a stack from anywhere in the swarm

swarmexec logs [flags] <service|service.slot|task-id|container-id>...

Stream logs from anywhere in the swarm.

One target that is one container streams exactly as before. Several targets, a service with several replicas, or --stack follow every source at once: each line is prefixed with where it came from (svc.slot, svc@node for a global service), each source reconnects across its own container replacements, and each has its own format detection.

A service (or service.slot) with no running container — crash-looping, failing its health check — shows the newest exited container of each slot instead, so the logs that say why it fails are one command away.

--min-level filters the log output shown here; swarmexec's own logging is the global --client-log-level.

Examples

swarmexec logs -f --tail 100 web swarmexec logs --grep 'timeout|refused' -f web swarmexec logs -f --tail 20 --stack shop
FlagDefaultDescription
--connect-timeout duration10stimeout for connecting to the agent
-f, --followfalsekeep streaming new log lines
--grep string—only show lines whose message matches this regexp
--log-format string—parse lines as: auto | classic | json | logfmt | gelf | raw (auto detects it from the lines themselves; default from config, else classic)
--min-level string—only show this level and above: trace|debug|info|warn|error|fatal
--node string—node hint/override for container-id targets
--since duration0sonly logs newer than this (e.g. 10m, 1h; 0 = no limit)
--stack string—follow every service of this stack (in addition to any targets)
--tail uint320number of lines from the end to start with (0 = all)
-t, --timestampsfalseprefix each line with a timestamp

Also takes the global flags and the connection flags.

swarmexec mcp

Serve the swarm to an AI assistant over MCP (stdio)

swarmexec mcp [flags]

Run a Model Context Protocol server on stdin/stdout, so an AI assistant can inspect the swarm: services, tasks, logs, stats, stack diffs. Register it with

claude mcp add swarmexec -- swarmexec mcp

A service is visible only with the service label swarmexec.mcp.enable=true (compose: deploy.labels). swarmexec.mcp.logs=true allows its logs, swarmexec.mcp.exec=true a non-interactive command in its containers. An explicit "false" always wins. --default read makes unlabelled services visible, never readable or executable.

The labels themselves are never shown to the assistant, and nothing can be changed through this server. A service that mounts the Docker socket is never exec'd into, whatever its labels say.

ssh cannot prompt here: stdin and stdout are the protocol. Load the key for an ssh:// context into ssh-agent first. Logging goes to the log file.

Only the docker context the server starts with (--context, $DOCKER_CONTEXT, $DOCKER_HOST or docker's current one) is reachable, plus those named with --contexts. Every other context does not exist as far as the assistant can tell: it is not listed, and asking for it is "unknown docker context".

Masking secrets in env and inspect output is cosmetic once exec is granted: a command run in the container can print its environment.

FlagDefaultDescription
--allow strings—enable optional tools: report (security_report)
--connect-timeout duration10stimeout for connecting to an agent
--contexts strings—further docker contexts the assistant may use, besides the one the server starts with (comma list or repeated)
--default stringnoneaccess for services without swarmexec.mcp.enable: none | read

Also takes the global flags and the connection flags.

swarmexec port-forward

Forward a local port to a port inside a container in the swarm

swarmexec port-forward [flags] <service|service.slot|task-id|container-id> [local:]remote

Aliases: pf

Forward a local TCP port to a port inside a container anywhere in the swarm, without publishing that port on the cluster.

The local port defaults to the remote one, so `port-forward api 8080` listens on 127.0.0.1:8080 and forwards to port 8080 in the container.

Targeting a service forwards to exactly ONE of its tasks (the one the target resolves to), not across all replicas — a forward that silently load-balanced would make debugging misleading.

Examples

swarmexec port-forward db 5432 swarmexec pf web 9090:8080 swarmexec port-forward web.2 8080
FlagDefaultDescription
--address string127.0.0.1local address to bind; loopback by default so the forwarded port is not exposed to your network
--connect-timeout duration10stimeout for connecting to the agent
--node string—node hint/override for container-id targets

Also takes the global flags and the connection flags.

swarmexec secret rotate

Replace a secret's content, keeping its name

swarmexec secret rotate <name> (--from-file FILE | --from-stdin) [flags]

Give a secret new content without renaming it, so stack files that name it stay valid. Swarm secrets are immutable and cannot be removed while in use, so every service using it is parked on a temporary secret meanwhile:

1  create <name>_rotating with the new content (same labels + a marker)
2  switch every service to <name>_rotating          (rolling update)
3  remove the old <name>
4  create <name> again: new content, original labels
5  switch every service back to <name>              (rolling update)
6  remove <name>_rotating

Only the secret behind each mount changes: target path, uid, gid and mode stay. Every service using the secret restarts twice. There is no rollback to the old content — the old secret object is deleted.

The value is sent byte for byte (nothing trimmed or added), must not be empty and is limited to 500 KB. It is never printed.

If a run stops half-way, the services keep running on <name>_rotating, which holds the new content. Run the same command again to finish: it reads where the last run stopped and continues there.

If the secret came from a stack file with `file:`, put the new content in that file too, or the next `docker stack deploy` fails on the changed data.

Without --yes, the services that will restart are listed and a y/N answer is read from the terminal; without a terminal, --yes is required.

Exit code 0 means rotated, 1 a failure (the message names the step and, when there is something to resume, how), 2 a usage error, 125 an unreachable manager.

Examples

swarmexec secret rotate db_password --from-file ./db_password.txt printf %s "$NEW" | swarmexec secret rotate api_token --from-stdin --yes
FlagDefaultDescription
--from-file string—read the new value from this file
--from-stdinfalseread the new value from stdin
--timeout duration5m0show long to wait for each service's rolling update
-y, --yesfalsedo not ask for confirmation

Also takes the global flags and the connection flags.

swarmexec stack deploy

Deploy a stack file, after checking it for security antipatterns

swarmexec stack deploy <file> [stack] [flags]

Load a stack file, run the security checks over what it would actually deploy, and apply it. The stack name defaults to the file's base name.

If anything above informational is found the deploy STOPS and asks. Use --yes to answer in advance (for CI), or --check to look without deploying. --force deploys despite findings without asking — say it deliberately.

FlagDefaultDescription

swarmexec stack diff

Compare a stack file against the deployed stack

swarmexec stack diff <file> [stack] [flags]

Show what deploying <file> would change. The stack name defaults to the file's base name, the same default `docker stack deploy` does not have — give it explicitly when the file is not named after the stack.

A "+" line is something deploying the file would add, a "-" is something it would remove. Both sides are normalised the same way, so an unchanged stack produces an empty diff rather than pages of daemon defaults.

Exit code 0 means no difference, 1 a difference, 2 a usage error and 125 an unreachable manager — so it can gate a pipeline. --ignore leaves a field out of both sides ("services.*.deploy.replicas" for an autoscaled count) and is reported under "Not compared"; --format json is the machine form.

FlagDefaultDescription
--format stringtextoutput format: text | json
--ignore strings—leave this field path out of both sides, e.g. services.*.deploy.replicas (repeatable)
--stack string—stack name to compare against (default: the file's base name)

Also takes the global flags and the connection flags.

swarmexec wait

Wait until services have converged — for CI after a deploy

swarmexec wait [flags] <service>...

Block until every named service (or every service of --stack) has converged, then exit 0. Exit 1 with the reason when one does not converge in time, when its update paused, or when it was rolled back during the wait.

Converged means: no update in flight, as many running tasks as desired (for a job: its completions reached), held for two polls in a row. With --healthy every container that has a healthcheck must also report healthy; a node whose agent cannot report health counts as "not yet", never as healthy.

FlagDefaultDescription
--connect-timeout duration10stimeout for connecting to an agent (--healthy)
--healthyfalsealso require every container with a healthcheck to be healthy (asks the agents)
--stack string—wait for every service of this stack (in addition to any named)
--timeout duration5m0sgive up after this long (exit 1)

Also takes the global flags and the connection flags.
