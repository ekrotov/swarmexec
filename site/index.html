The manager says running. Ask the node.

In a Swarm the manager knows where every task is scheduled. What is true inside the container — its healthcheck, its shell, a port nobody published, the volume on its disk — lives on one node. swarmexec puts a small agent on every node and asks it directly, from the terminal you are already sitting in.

No SSH to whichever node runs the task, no throwaway helper container per command. Apache-2.0, no node limit.

Three things you will not find elsewhere

Exec by itself is no longer rare — d4s has it over an SSH tunnel, and swarmcli's Business Edition behind an mTLS proxy. These three have not turned up in either, nor in Portainer, Swarmpit or Komodo.

$ swarmexec stack diff web.yml

A diff of what would change, not of how it is spelled

A deployed stack carries things your file never had: the digest the daemon resolved, its own restart and update defaults, the stack name prefixed onto every network and secret. Compared as text, that is a page of differences for a stack that is exactly in sync — and a tool that teaches you to ignore its output.

swarmexec runs the file through Docker's own compose loader and converter, the code docker stack deploy uses, and reduces both sides with the same function. The question it answers is would deploying this change anything. Exits 1 on a difference, like git diff --exit-code.

An export is a description, not a backup: secret values are write-only in the engine API and volume contents live on the nodes, so both are declared external, and the output says so under Not compared.

$ swarmexec stack deploy web.yml --check

A scan of the spec, before anything is created

Eight analyzers read each service's spec — the spec the manager already returned, so nothing runs inside your containers. stack deploy converts the file into the very ServiceSpec values it would submit and runs the same eight, so the gate, the 🛡 in the tree and the report can never disagree.

Anything above informational stops the deploy and asks. --yes means do not ask, not ignore the findings — it still refuses. To deploy anyway you type --force.

security report adds four checks no single service can answer: unencrypted overlay networks, managers without autolock, agent version skew, secrets and configs nobody references — and names what it could not reach, because silence in a security report reads as an all-clear.

Tap a line to change it. The output is the checker's, rule for rule.

services:

Also found, and not printed because it is informational: image not pinned.

$ swarmexec logs -f web.2

Logs that outlive the container

A rolling update, a restart or a reschedule replaces the container under the stream. The client re-resolves the slot through the manager it is already talking to, dials the new node's agent and prints one dim line where the old stream ended. It waits about 30 seconds for a replacement to be scheduled, and stops cleanly if the service is removed.

The detection has to live in the client: each agent is local to its node and cannot see a replacement that happens at the swarm level.

The whole command surface

Every command honours your Docker CLI context, including an ssh:// one behind a jump host. Connections to the same host share one OpenSSH transport, so only the first one authenticates: doctor on a three-node cluster behind a jump host went from 8 authentications and 3.6 s to 2 and 1.0 s.

Provision

init
deploy the agent as a global service, create the shared secret, write a matching client config
init --force
re-roll the agents and keep the secret, so every client keeps working
down
remove the agents again; your client config is left alone
doctor
check the manager and every agent; non-zero if one is unhealthy or too old

Reach in

exec <target> -- sh
a shell or a one-off command in any container; the remote exit code comes back verbatim
logs -f <target>
follow across replacement; --log-format auto, --min-level, --grep
port-forward <target>
a local port onto a container port that is published nowhere
ps
every task and the node it runs on, from the manager alone

Node-local objects

volume ls
volumes across all nodes, with which nodes hold each and who uses it
volume rm
remove a volume on every node that holds it, or on the nodes you name
context
create, list and switch Docker contexts, in docker's own store
config show
the effective merged config, secret masked

Stacks and safety

stack export
read a deployed stack back out as compose-shaped YAML
stack diff
compare a file against what is deployed; exits 1 on a difference
stack deploy
check the file, then apply it; --check gates a pipeline
security report
a Markdown audit of services, networks, secrets and nodes

A target is web (the service's running task), web.2 (a replica slot), xxh8k1… (a task ID) or 3f9a2b… (a container ID). A bare service name with several replicas is ambiguous: exec offers a numbered list when it is interactive; logs and port-forward print the candidates and exit rather than pick for you.

The same cluster, as one screen

swarmexec ui has seven tabs — Stacks/Services, Volumes, Forwards, Networks, Secrets, Nodes, Configs — a context sidebar on the right, and exec, logs and port-forwarding built in.

  • The tree is coloured by healthcheck as well as replica count — the rule the stage above lets you try.
  • A service with a finding worth acting on carries a 🛡 in a fixed-width column, so the shields line up into a vertical scan.
  • CPU and memory markers appear at 70 % and 90 %, measured against the container's own limit when it has one.
  • Switching context keeps your place, your filters and your forwards.
  • ? opens the full key reference, generated from your own keymap.

Health and usage need agents from a current release. A cluster that has not been re-rolled shows neither, rather than a guess — init --force fixes that.

What the scan looks for

The report's own Checked list is generated from the analyzers themselves, so a check cannot ship without appearing in what the report claims to have looked at.

Per service, from the spec the manager returned
CheckSeverityWhat it flags
docker-sockethighthe daemon socket bind-mounted in. Anything that can talk to it can start a privileged container on that node; read-only does not help, because a socket is an API, not a file.
added-capabilityhigh mediumSwarm has no --privileged, so capabilities are how a service asks for host power. Eight are high, each with its reason: ALL, SYS_ADMIN, SYS_MODULE, SYS_PTRACE, SYS_RAWIO, DAC_READ_SEARCH, NET_ADMIN, NET_RAW. Any other is medium.
host-networkhighattached to the host network: no isolation, no port mapping, and it can reach anything the node can — including services bound to localhost.
unconfinedhighseccomp or AppArmor switched off, reported separately, so a service that disables both gets two findings.
root-userhigh lowhigh when the spec pins the container to root — User=root or uid 0. Low, and not marking the service, when no user is set at all: whether that is root depends on the image's own USER.
secret-in-envhigha credential-looking key with a literal value, readable by anyone who can read the spec. *_FILE references are exempt, and the value never appears in the finding.
no-resource-limitslowneither a CPU nor a memory limit, so a runaway container can starve the node.
unpinned-imagelow:latest or no tag. A digest-pinned image is never flagged, and a registry port is not mistaken for a tag.
Per cluster, in the Markdown report
CheckSeverityWhat it flags
network-unencryptedmediumSwarm tunnels traffic between nodes over VXLAN in the clear unless the network was created --opt encrypted. Empty networks are not flagged, nor is ingress, which cannot be encrypted at all.
autolock-disabledmediumthe raft store holds every secret, every config and the cluster CA key, and its key sits on the same disk. Unreadable configuration is reported as unknown, not guessed.
agent skewhigh medium lowthe agent enforces authorization, so one older than your client may not enforce a rule the client assumes. An agent that did not answer is a gap, not a pass.
unused-secret / -configlowstill distributed through raft and readable by anything that reaches a manager — usually a credential someone rotated and never removed.

The report is written 0600 into directories created 0700: it names every service, network and secret together with every weakness found in it, which is a map of where to attack. Its order depends only on the findings, so two reports of an unchanged cluster differ in their timestamp alone.

Setting it up

  1. Take the binary

    $ curl -fsSL https://swarm-exec.cloud-surfers.net/install.sh | sh
$ brew install ekrotov/swarmexec/swarmexec        # macOS, Linux
$ scoop bucket add swarmexec https://github.com/ekrotov/scoop-swarmexec
$ scoop install swarmexec                          # Windows

    One static binary. The install script checks it against the release's checksum and refuses what it cannot verify. Docker Engine 19.03 or newer on the manager and every node; live usage and the per-node image view want 23.0 and say so instead of failing below it.

  2. Provision the agents, once

    $ swarmexec --context prod init

    Deploys the agent as a global service — one task per node — creates a shared secret and writes the matching client config. swarmexec down takes it away again.

  3. Use it

    $ swarmexec exec web -- sh
$ swarmexec ui

    Or put stack diff and stack deploy --check into CI, where the exit codes are the point.

Two ways to authenticate

Mutual TLS

The recommended posture. Your own CA — the project does no PKI bootstrap. The agent identifies and audits you by your certificate's CN.

Shared secret

What init sets up: one secret, no PKI. The secret itself is never sent — the client sends a proof bound to the certificate of the connection it travels on, so a server you did not verify receives nothing that works against a real agent. That beats theft and replay, not eavesdropping; for that you want a CA.
