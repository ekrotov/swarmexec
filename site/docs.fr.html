swarmexec_ docs

Prendre en main le client — commandes, options, configuration & la TUI.

swarmexec vous offre docker exec -it, les logs, la redirection de ports et la gestion des volumes pour n'importe quel conteneur d'un Docker Swarm, depuis un seul terminal. Un petit agent par nœud (un service Swarm global) fait le travail sur son nœud ; le client demande au manager Swarm quel nœud exécute votre cible, puis se connecte directement à l'agent de ce nœud en mTLS. Cette page documente le client.

1. Fonctionnement

Deux binaires, un seul protocole réseau :

  • agent — s'exécute comme un service Swarm global (une tâche par nœud), monte le socket Docker de ce nœud et expose une API gRPC restreinte qui relaie exec / logs / redirection de ports vers les conteneurs de son propre nœud. Vous le déployez une seule fois avec swarmexec init.
  • client (cette CLI) — s'exécute sur votre poste de travail. Il interroge l'API du manager Swarm pour déterminer quel nœud exécute votre cible et l'id du conteneur, puis se connecte directement à l'agent de ce nœud sur le port 9443. Les agents ne communiquent jamais entre eux.
terminal opérateur ──gRPC/mTLS──> agent(nœudN) ──docker.sock──> conteneur │ └── API du manager Docker (résout le nœud + l'id du conteneur)

La connexion au manager utilise votre contexte de la CLI Docker (elle respecte donc --context, les bastions ssh://, mTLS, etc.). La connexion à l'agent est authentifiée par TLS mutuel, ou par un secret partagé face à un agent auto-signé — voir Authentification.

2. Installation

Nécessite Docker Engine 19.03 ou plus récent (API 1.40) sur le manager et sur chaque nœud. swarmexec refuse un démon plus ancien dès la connexion, avec un message qui indique les deux versions, plutôt que de se connecter puis d'échouer vue après vue. Deux fonctionnalités en demandent un peu plus au démon du nœud : l'utilisation des ressources en direct et la vue des images par nœud exigent Docker 23.0 (API 1.41/1.42) ; en deçà, elles restent vides et le signalent, au lieu d'échouer.

Le plus rapide : le script d'installation choisit le binaire adapté à votre machine, le vérifie avec le SHA256SUMS de la release et refuse d'installer ce qu'il n'a pas pu vérifier. Il n'utilise jamais sudo et ne modifie jamais votre profil shell — lisez-le d'abord, il est court.

$ curl -fsSL https://swarm-exec.cloud-surfers.net/install.sh | sh $ curl -fsSL https://swarm-exec.cloud-surfers.net/install.sh | SWARMEXEC_VERSION=v1.19.2 sh # une release précise

Avec un gestionnaire de paquets — brew upgrade ou scoop update récupèrent alors chaque nouvelle release, ce qui maintient le client à la même version que les agents :

$ brew install ekrotov/swarmexec/swarmexec # macOS, Linux $ scoop bucket add swarmexec https://github.com/ekrotov/scoop-swarmexec $ scoop install swarmexec # Windows

Ou à la main :

Le client est un binaire statique unique. Téléchargez le build de la dernière release pour votre plateforme :

$ curl -fsSLo swarmexec \ https://gitlab.logle.io/cs-public/swarm-remote-exec/-/releases/permalink/latest/downloads/bin/swarmexec-linux-amd64 $ chmod +x swarmexec && sudo mv swarmexec /usr/local/bin/ $ swarmexec --version

Builds : linux-amd64, linux-arm64, darwin-arm64, darwin-amd64, windows-amd64. L'image de l'agent est publiée sur Docker Hub sous le nom logleio/swarmexec-agent.

Complétion dans le shell

swarmexec completion bash|zsh|fish|powershell affiche un script de complétion. Il complète davantage que les options : exec <TAB> propose les services existants, logs web.<TAB> leurs slots en cours d'exécution, --stack <TAB> les stacks déployées et --context <TAB> vos contextes Docker. Seule l'API du manager est interrogée, jamais un agent ; une complétion abandonne au bout de deux secondes et, via ssh://, n'a jamais le droit de demander une saisie : un contexte qui exigerait un mot de passe ne propose alors rien, au lieu de bloquer le shell.

$ swarmexec completion bash > /etc/bash_completion.d/swarmexec # ou ~/.local/share/bash-completion/completions/ $ swarmexec completion zsh > "${fpath[1]}/_swarmexec" $ swarmexec completion fish > ~/.config/fish/completions/swarmexec.fish

3. Démarrage rapide

Pointez votre contexte Docker sur un manager Swarm, puis provisionnez les agents, une seule fois. init crée un secret partagé, déploie l'agent sur chaque nœud en mode auto-signé et écrit la configuration client correspondante — les autres commandes fonctionnent donc immédiatement.

$ swarmexec --context my-swarm init # déployer les agents sur chaque nœud (une fois) $ swarmexec ps # lister les tâches et le nœud sur lequel chacune s'exécute $ swarmexec exec web -- sh # ouvrir un shell dans le service « web », n'importe quel nœud $ swarmexec logs -f web # suivre les logs d'un service $ swarmexec port-forward db 5432 # localhost:5432 → conteneur:5432 $ swarmexec ui # TUI interactive

Pour retirer les agents, utilisez swarmexec down (votre configuration client reste intacte).

4. Sélecteurs de cible

exec, logs et port-forward prennent une cible comme premier argument. Elle est résolue dans l'ordre suivant :

FormeExempleSignification
servicewebLa tâche en cours d'exécution du service. S'il a plus d'un réplica, la cible est ambiguë — voir ci-dessous.
service.slotweb.2Un slot de réplica précis. Pendant une mise à jour progressive, c'est la tâche la plus récente du slot qui l'emporte.
task-idxxh8k1…Un ID de tâche Swarm.
container-id3f9a2b…Un préfixe d'ID de conteneur. Nécessite un nœud : passez --node, sinon il est déterminé en parcourant les tâches en cours d'exécution.

Ambiguïté. Un simple nom de service à plusieurs réplicas ne peut pas être résolu en une seule tâche. En mode interactif, exec vous fait choisir dans une liste numérotée ; logs et port-forward ne posent jamais la question — ils affichent la liste des candidats et s'arrêtent. Levez l'ambiguïté en précisant un slot (web.0, web.1, …).

--node n'est pris en compte que pour les cibles de type container-id et peut être un nom d'hôte, une IP ou un ID de nœud. Les cibles service / slot / tâche sont localisées via l'API du manager et n'en ont donc jamais besoin.

5. Configuration

Les paramètres proviennent de quatre niveaux, chacun l'emportant sur le précédent :

valeurs par défaut intégrées → fichier de config → environnement → options en ligne de commande

Une option ne l'emporte que si vous la passez effectivement : une valeur du fichier ou de l'environnement est donc conservée tant qu'elle n'est pas explicitement remplacée.

Fichier de configuration

Le chemin par défaut est le premier défini parmi les suivants :

  1. $SWARMEXEC_CONFIG
  2. $XDG_CONFIG_HOME/swarmexec/config.yaml
  3. ~/.config/swarmexec/config.yaml

Remplacez-le avec --config <path>. Le fichier est en YAML ; un fichier absent ne pose pas de problème, un fichier mal formé est une erreur. Il est écrit avec les droits 0600 (il peut contenir le secret partagé). Par défaut, le fichier de log se trouve à côté — ~/.config/swarmexec/swarmexec.log — sauf si vous définissez --log-file. 6. Authentification

Le client s'authentifie auprès de l'agent selon l'un des deux modes suivants.

Mode A — TLS mutuel (par défaut)

Définissez ca, cert et key (les trois requis). Le client vérifie l'agent auprès de votre CA et présente son certificat ; l'agent vous autorise et trace vos actions d'après le CN du certificat. C'est le mode par défaut et la configuration recommandée.

$ swarmexec --ca ca.crt --cert me.crt --key me.key ps

Mode B — agent auto-signé + secret partagé

Plus simple à exploiter (un secret, pas de PKI) — c'est ce que met en place init. Définissez agent_secret (ou agent_secret_file), et soit un ca pour vérifier l'agent soit insecure: true pour ignorer la vérification. Un certificat client est facultatif (mais cert et key doivent être définis ensemble, ou rester vides tous les deux). Votre identité d'audit est la valeur operator (par défaut : votre nom d'utilisateur système).

$ swarmexec --agent-secret "$SECRET" --insecure ps
insecure désactive la vérification du certificat serveur de l'agent. Cela ne met pas le secret en danger : le client ne l'envoie jamais, seulement une preuve calculée à partir du secret et du certificat de la connexion qui la transporte — un serveur que vous n'avez pas vérifié ne reçoit donc rien d'utilisable contre un véritable agent. En revanche, l'agent ne s'authentifie pas auprès de vous : quiconque répond peut lire ce que cette session lui envoie. Préférez un ca sur tout réseau auquel vous ne faites pas confiance, et gardez le secret hors de l'historique de votre shell (utilisez agent_secret_file ou le fichier de configuration).

Passage à la v1.17.3 — mettez d'abord les agents à jour

Un client v1.17.3 ne peut pas s'authentifier auprès d'un agent plus ancien. Il n'envoie que la preuve liée à la connexion, et les agents antérieurs à la v1.17.3 ne connaissent pas cette forme : ils répondent invalid or missing agent secret alors même que votre secret est correct. Mettez-les à jour d'abord :
$ swarmexec init --force
Tant que le parc mélange les versions, legacy_secret: true dans la configuration du client envoie aussi le secret brut, avec l'exposition décrite ci-dessus. Retirez-le dès que les agents sont à jour, puis relancez swarmexec init --force --allow-legacy-secret=false pour qu'aucun client ne puisse faire transiter l'identifiant sur le réseau par mégarde.

7. Contexte Docker & SSH

--context sélectionne le contexte de la CLI Docker utilisé pour l'API du manager. Ordre de résolution : --context → $DOCKER_CONTEXT → $DOCKER_HOST → le contexte actif dans ~/.docker/config.json → le socket local unix:///var/run/docker.sock.

Aucun Docker local requis. Le client n'exécute jamais le binaire docker — il embarque le SDK Go de Docker et s'adresse directement à l'API du manager, en lisant lui-même les métadonnées de contexte dans les fichiers. Il lui suffit d'un point d'accès manager Swarm joignable (les appels qui résolvent les nœuds ne fonctionnent qu'auprès d'un manager) :
  • $DOCKER_HOST pointant vers un manager tcp:// distant (mTLS) — Docker n'a alors pas du tout besoin d'être installé sur votre poste de travail ;
  • un contexte ssh:// — nécessite le client ssh (pas docker) ; le trafic vers le manager comme vers les agents passe par ce tunnel ;
  • le socket local unix:///var/run/docker.sock — ce n'est que le choix de repli par défaut, et la seule option qui suppose un démon local.
La CLI docker elle-même ne sert qu'à créer des contextes nommés (docker context create) — et même cela peut se faire avec swarmexec context create <name> --docker-host …, sans la CLI docker ; utilisez $DOCKER_HOST pour vous passer complètement des contextes nommés. (init ne lit les identifiants du docker login local que pour une image d'agent privée — pas pour l'image publique par défaut.)

Bastion SSH. Si l'hôte du contexte est un point d'accès ssh://, l'API du manager passe par un tunnel SSH — tout comme la connexion à l'agent : les points d'accès node:9443 des nœuds n'étant généralement pas routables depuis votre poste de travail, le client fait passer automatiquement le trafic gRPC de l'agent par le même hôte SSH. Aucune option supplémentaire n'est nécessaire.

$ docker context create swarm --docker host=ssh://ops@manager.example.com $ swarmexec --context swarm exec web -- sh

wait — attendre qu'un déploiement ait réellement convergé

stack deploy rend la main dès que swarm a accepté le changement, pas quand celui-ci fonctionne. wait comble cet écart dans un pipeline : la commande attend que chaque service nommé — ou chaque service de --stack — ait convergé, puis se termine avec le code 0 ; si l'un d'eux ne converge pas, elle se termine avec le code 1 en indiquant la raison.

swarmexec stack deploy shop.yml --yes && swarmexec wait --stack shop --timeout 3m swarmexec wait api worker --healthy

Convergé signifie : aucune mise à jour en cours et autant de tâches en cours d'exécution que souhaité (pour un job : le nombre d'exécutions terminées atteint), et ce sur deux relevés à quelques secondes d'intervalle — même un service stable demande donc quelques secondes, et l'instant qui suit un déploiement, avant que le manager ait lancé la mise à jour, ne peut pas passer pour un succès. Deux états d'apparence stable sont des échecs : une mise à jour en pause (le service exécute un mélange d'anciennes et de nouvelles tâches) et un retour arrière (rollback) achevé pendant l'attente (le service exécute la spec précédente — le déploiement n'a pas pris). En cas d'expiration du délai, la raison pour laquelle une tâche ne tourne pas est affichée, généralement le message de l'ordonnanceur lui-même. Avec --healthy, chaque conteneur doté d'un healthcheck doit en outre être sain ; un nœud dont l'agent ne peut pas indiquer l'état de santé compte comme pas encore prêt, jamais comme sain. swarmexec se contente d'observer et de rapporter — il ne fait jamais de retour arrière ni de nouvelle tentative.

OptionDéfautDescription

--timeout5mabandonne au bout de cette durée (code de sortie 1)
--healthyfalseexige en plus des conteneurs sains (interroge les agents)

doctor — diagnostiquer le swarm

Vérifie la connexion au manager et la présence du service de l'agent, puis sonde l'agent de chaque nœud prêt pour contrôler qu'il est joignable et détecter les écarts de version. Affiche un tableau par nœud (NODE  AGENT  VERSION  PROTO) ; se termine avec un code non nul si le manager est injoignable ou si un agent est défaillant. Un nœud signalé too old (init --force) exécute un agent plus ancien que votre client — voir redéployer les agents sans changer le secret.

swarmexec doctor

security report — un rapport Markdown sur tout le cluster

La surcouche des risques de sécurité analyse les specs des services et affiche le résultat à l'écran. Cette commande écrit la même analyse — plus les contrôles qui relèvent du cluster et non d'un service en particulier — au format Markdown, pour la relire hors du terminal, la joindre à un ticket, ou la committer à côté de vos fichiers de stack et la comparer d'une release à l'autre. La sortie va sur stdout sauf si -o est fourni : elle se redirige aussi facilement qu'elle s'enregistre.

swarmexec security report -o security.md

Quatre contrôles s'exécutent au niveau du cluster ; aucun ne peut être tranché par la spec d'un service :

ContrôleGravitéCe qu'il signale
network-unencrypted — « le trafic overlay n'est pas chiffré »mediumun réseau overlay transportant du trafic de services sans chiffrement du plan de données. Swarm fait transiter le trafic des conteneurs entre les nœuds dans des tunnels VXLAN en clair, à moins que le réseau n'ait été créé avec --opt encrypted, et rien ne distingue le service en fonctionnement dans un cas comme dans l'autre. Les réseaux auxquels rien n'est attaché ne sont pas signalés — ils ne transportent rien — pas plus qu'ingress, qui ne peut pas du tout être chiffré : un constat le concernant ne pourrait jamais être levé
autolock-disabled — « l'autolock des managers est désactivé »mediumle magasin raft des managers n'est pas chiffré au repos. Il contient tous les secrets, toutes les configs et la clé de la CA du cluster, et sa clé de chiffrement se trouve sur le même disque : qui récupère le disque d'un manager récupère tout. Activez l'autolock avec docker swarm update --autolock=true et conservez la clé de déverrouillage : un manager redémarré la demandera. Si la configuration du swarm ne peut pas être lue, le rapport indique autolock-unknown plutôt que de deviner — supposer « désactivé » inventerait un constat, et supposer « activé » donnerait un faux feu vert

Une incompatibilité de protocole est high et prime sur un écart de version : les deux extrémités sont en désaccord sur le contrat lui-même, et pas seulement sur le build qui l'implémente. Un agent qui n'a pas répondu est signalé comme une zone non couverte, pas comme un succès. Aucun écart n'est signalé pour un client non publié (dev), qui diffère par construction de tout agent publié — la même exception que fait doctor
unused-secret / unused-configlowun secret ou une config qu'aucun service ne référence. Il reste distribué par le magasin raft et lisible par quiconque atteint un manager — le plus souvent un identifiant renouvelé sans que l'ancien soit supprimé, si bien que l'ancienne valeur est toujours active dans le cluster longtemps après que tout le monde la croit disparue

Ce que le rapport dit de lui-même. Il est lu hors du terminal, par quelqu'un qui n'était pas là lors de son exécution : il porte donc son propre contexte — quel cluster, quand, avec quel build. Il comporte aussi une section Not covered — agents injoignables, configuration du swarm illisible, liste de nœuds vide — parce que, dans un rapport de sécurité, le silence se lit comme un feu vert sur un terrain jamais examiné. L'ordre ne dépend que des constats : deux rapports d'un cluster inchangé ne diffèrent que par leur horodatage et peuvent être comparés l'un à l'autre — ce qui n'a de valeur que parce qu'un constat absent signifie non trouvé, jamais non examiné.

Le fichier est écrit en 0600, et les répertoires parents éventuels sont créés en 0700. Il nomme chaque service, réseau et secret du cluster avec chaque faiblesse relevée : c'est une carte des points d'attaque, qui n'a pas à être lisible par tous les comptes de la machine.

Le même rapport peut être écrit depuis la TUI : appuyez sur w dans la surcouche des risques de sécurité. stack export / stack diff — une stack déployée sous forme de fichier

stack export relit une stack déployée dans le cluster et l'écrit en YAML au format compose. stack diff compare un fichier de stack à ce qui est réellement déployé et affiche un diff unifié : une ligne + correspond à ce que le déploiement du fichier ajouterait, une ligne - à ce qu'il retirerait. Comme git diff --exit-code, la commande se termine avec le code 1 dès qu'il y a une différence : elle s'utilise donc en CI.

swarmexec stack ls swarmexec stack export postgres -o postgres.yml swarmexec stack diff postgres.yml postgres

Dans la TUI, E sur l'onglet Stacks/Services propose les deux pour la stack sous le curseur — que le curseur soit sur la ligne de la stack, sur l'un de ses services ou sur l'un de leurs conteneurs.

Pourquoi ce n'est pas une comparaison de texte. Une stack déployée contient ce que le fichier n'a jamais eu : le digest de l'image résolu par le démon au déploiement, ses propres valeurs par défaut pour les politiques de redémarrage et de mise à jour, et l'espace de noms de la stack préfixé à chaque réseau, secret et volume. Comparer les deux comme du texte signale des dizaines de différences pour une stack parfaitement synchronisée — ce qui est pire que pas d'outil du tout, puisque cela apprend à ignorer la sortie. Le fichier passe donc par le chargeur et le convertisseur compose de docker lui-même, le code qu'utilise docker stack deploy, puis les deux côtés sont normalisés par la même fonction. La question posée est « déployer ce fichier changerait-il quelque chose ? », pas « ces deux fichiers sont-ils écrits pareil ? ». Les valeurs par défaut du démon sont retirées des deux côtés ; une valeur qui n'est pas celle par défaut apparaît toujours : aucune différence réelle n'est masquée.

Un export est une description, pas une sauvegarde. La valeur d'un secret est en écriture seule dans l'API du moteur — elle ne peut jamais être relue — et le contenu d'un volume réside sur les nœuds. Les deux sont donc déclarés external, et le fichier exporté le précise dans son en-tête : recréer la stack ailleurs suppose de créer d'abord les secrets. Les champs de la spec que ce rendu ne reprend pas (tty, ulimits, réglages seccomp et AppArmor, et quelques autres) sont énumérés au même endroit, car le pire défaut d'un outil de comparaison n'est pas une réponse fausse mais un silence trop sûr de lui : « aucune différence » est toujours accompagné de ses réserves.

Les variables sont interpolées depuis votre environnement, exactement comme le fait docker stack deploy. Un fichier contenant ${TAG} décrit donc une stack différente pour un TAG différent, et le diff dépend de l'environnement dans lequel il s'exécute — ce qui est correct : faire autrement signalerait « aucun changement » pour un déploiement qui changerait l'image.

CommandeDescription
stack lsles stacks déployées sur le cluster
stack export <stack>écrit la stack en YAML compose ; avec -o dans un fichier, sinon sur stdout
stack diff <file> [stack]compare un fichier à la stack déployée. Par défaut, le nom de la stack est celui du fichier sans extension ; --stack ou un second argument le remplace. Se termine avec le code 1 à la moindre différence

Comme garde-fou de pipeline. Lancé chaque nuit, stack diff répond à la question « le cluster correspond-il toujours à Git ? » : le code 0 signifie aucune différence, 1 une différence, 2 une erreur d'utilisation, 125 un manager injoignable. Un contrôle qui passe au rouge à chaque changement anodin finit désactivé ; d'où --ignore, qui retire un champ des deux côtés — services.*.deploy.replicas pour un nombre de réplicas qu'un autoscaler fait varier, * remplaçant n'importe quel nom de service ; répétez l'option pour plusieurs chemins. Chaque chemin ignoré est listé sous Not compared, pour qu'un résultat vert indique quand même ce qu'il n'a pas examiné, et un chemin qui ne correspond à rien, d'un côté comme de l'autre, est signalé : sans cela, une faute de frappe dans la liste n'ignorerait rien, en silence. --format json produit la sortie destinée aux machines : differs, les hunks, ignored et not_compared.

swarmexec stack diff shop.yml --ignore 'services.*.deploy.replicas' swarmexec stack diff shop.yml --format json | jq .differs

stack deploy — appliquer un fichier de stack, après vérification

Charge un fichier de stack, exécute les contrôles de sécurité sur ce qu'il déploierait réellement, puis l'applique. Son intérêt par rapport à docker stack deploy, c'est le garde-fou : le fichier est vérifié avant que quoi que ce soit ne soit créé, et si un constat plus grave que purement informatif est relevé, le déploiement s'arrête et demande confirmation.

swarmexec stack deploy web.yml # demande si quelque chose est trouvé swarmexec stack deploy web.yml --check # vérifier seulement, jamais déployer swarmexec stack deploy web.yml --force # déployer malgré les constats, délibérément

Dans la TUI, E → deploy a file fait de même : les constats s'affichent d'abord, d poursuit, Esc abandonne. À ce stade, rien n'a encore été créé — c'est précisément tout l'objet de cette pause.

Les contrôles ne sont pas un second jeu de règles. Le fichier est converti exactement en valeurs ServiceSpec, celles que le déploiement soumettrait, et les huit analyseurs existants s'exécutent dessus — les mêmes contrôles qui placent le bouclier dans l'arbre et alimentent la surcouche ! ainsi que le rapport de sécurité. Deux jeux de règles finiraient par diverger : une règle durcie d'un côté et pas de l'autre, et le garde-fou laisse passer un fichier que l'arbre signale dès qu'il est déployé — l'opérateur à qui l'on a répondu « rien trouvé » a reçu une information fausse. Les contrôles voient en outre ce que le cluster fera, et non ce que le fichier dit : les valeurs par défaut et les raccourcis de compose s'intercalent entre les deux.

--yes ne veut pas dire « ignorer les constats ». Cela veut dire « ne pas demander » : une exécution qui relève un constat plus grave que purement informatif refuse malgré tout et se termine avec un code non nul. Sinon, le garde-fou deviendrait une formalité dès sa première intégration en CI. Pour déployer malgré les constats, il faut écrire --force : autre chose à taper, et autre chose à justifier ensuite. Une exécution non interactive sans réponse sur stdin vaut non.

OptionDescription
--checkexécute les contrôles et s'arrête. Se termine avec le code 1 si un constat plus grave que purement informatif a été relevé : utilisable comme garde-fou de pipeline
-y, --yesne demande pas. Déploie si les contrôles ne relèvent rien ; refuse sinon
--forcedéploie malgré les constats, sans demander
--prunesupprime les services de la stack que le fichier ne déclare plus. Désactivé par défaut, comme dans docker : un fichier qui ne couvre qu'une partie de la stack relève bien plus souvent de l'erreur que d'une demande de suppression

Ce que fait un déploiement, dans l'ordre : réseaux, puis secrets, puis configs, puis services — un service qui référence un objet pas encore créé échoue, et la stack reste à moitié appliquée. Les réseaux externes sont vérifiés en premier, car un réseau inexistant est la cause la plus courante d'un déploiement interrompu à mi-chemin. Un secret existant n'est jamais écrasé : la valeur d'un secret est immuable dans swarm, et la changer implique d'en créer un nouveau sous un autre nom. Si un déploiement échoue malgré tout en cours de route, ce qui a déjà été appliqué est indiqué avec l'erreur, au lieu d'être laissé à deviner.

Surveiller les agents

Chaque agent peut servir des métriques Prometheus. Elles sont désactivées par défaut ; swarmexec init --force --metrics-port 9464 les active : l'agent écoute sur ce port et le publie en mode host sur chaque nœud, comme le port de l'agent ; Prometheus joint donc l'agent de chaque nœud sur <node>:9464. Le point d'accès est en HTTP simple et ne fournit que des compteurs — ni noms, ni identifiants, ni contenu —, mais ne le publiez que là où votre scraper peut l'atteindre.

Politique d'autorisation

Par défaut, un agent autorise toute requête authentifiée. Un fichier de règles restreint cela : quelles actions (container.list, container.events, exec, logs, portforward, stats.read, image.list, image.prune, image.prune.all, volume.list, volume.create, volume.remove ; les motifs comme volume.* sont acceptés) pour quels services, quels ports, quels utilisateurs d'exec et — avec des certificats client uniquement — quelles identités d'opérateur. Au sein d'une règle, toutes les conditions doivent être remplies ; la première règle qui correspond l'emporte, et default (obligatoire) couvre le reste.

# policy.yaml — la première règle qui correspond l'emporte ; « default » si aucune ne correspond default: allow rules: - deny: [image.prune.all] reason: no sweeping prune on production - deny: [portforward] ports: [5432, 3306] reason: no forwards to the databases - deny: [exec] users: [root, "0", "0:0"] - deny: ["volume.*"] services: ["prod_*"]
swarmexec init --force --policy-file policy.yaml

Un refus parvient au client sous la forme permission denied, avec la règle et sa raison, et le même texte est inscrit dans le journal d'audit. init vérifie le fichier avant tout déploiement, et l'agent refuse de démarrer avec un fichier qu'il ne sait pas lire : une action inconnue, une clé mal orthographiée ou un motif invalide est une erreur, jamais une règle qui ne correspond à rien sans prévenir. Les règles portant sur identities sont refusées tant que les agents utilisent un secret partagé sans certificats client — l'identité n'est alors que ce que le client prétend. Un exec sans -u s'exécute avec l'utilisateur de l'image, que l'agent ne connaît pas ; users: [""] le cible. Modifiez le fichier et relancez init --force ; relancez-le sans l'option pour retirer la politique.

Ce que ce n'est pas. Une politique évite les accidents et formalise une intention — pas de prune massif en production, pas de redirection vers la base de données. Ce n'est pas un contrôle d'accès : tout ce que swarmexec modifie sur les services, secrets, réseaux et stacks est envoyé au manager du swarm avec vos propres identifiants Docker, sans jamais passer par un agent, et qui détient ces identifiants peut déployer un service root sur chaque nœud. Pour cela, restreignez les identifiants Docker.

Redéployer les agents sans changer le secret

Tôt ou tard, vous devrez redéployer les agents sur un swarm déjà provisionné : un agent ne répond plus, doctor affiche un nœud en too old (init --force), une commande échoue avec « agent is older than this client (missing RPC) — update it with swarmexec init --force », ou un nœud a été réinstallé et son agent n'est jamais revenu. La solution consiste à relancer init avec --force, dont c'est exactement le rôle : mettre à jour le service s'il existe déjà. Sans cette option, lancer init alors que le service existe est une erreur d'utilisation qui vous invite à ajouter --force ; rien n'est modifié.

$ swarmexec init --force

L'agent est alors redéployé sur chaque nœud et le secret partagé reste inchangé. Les secrets Docker sont immuables : init retrouve le swarmexec_agent_secret existant, le signale comme reusing existing et conserve la valeur déjà présente dans le cluster. Tout client qui fonctionnait avant continue de fonctionner — il n'y a rien à redistribuer.

Ne passez pas --secret lors d'un redéploiement. Si le secret existe déjà, il ne peut pas être écrasé : votre valeur n'est pas appliquée au cluster, mais elle est tout de même écrite dans votre configuration client. À moins qu'elle ne corresponde à la valeur réelle du secret existant, les agents vous rejetteront à partir de ce moment, et la panne ne se manifeste que plus tard, sous les traits d'un agent défaillant plutôt que d'une configuration locale erronée. init avertit précisément dans ce cas ; prenez cet avertissement au sérieux. Pour changer réellement le secret du cluster, vous devez d'abord supprimer le secret (aucun service ne doit le référencer) puis relancer init.

--save-config vaut true par défaut : un redéploiement réécrit donc aussi ~/.config/swarmexec/config.yaml. Passez --save-config=false dès que la configuration client locale doit rester intacte — par exemple lorsque vous redéployez les agents depuis une machine dont la configuration est déjà correcte, ou depuis la CI.

$ swarmexec init --force --save-config=false

Vérifiez ensuite. doctor indique un état par nœud ; ok sur tous les nœuds signifie que client, agents et secret sont de nouveau en phase.

$ swarmexec doctor

Analyse & filtrage selon le format. --log-format indique au client comment lire chaque ligne pour en extraire un niveau et un message : classic extrait un niveau d'une ligne de texte brut — un champ entre crochets ([error], [ info]), un mot en MAJUSCULES ou un mot suivi d'un deux-points (error:) — c'est ce qui évite qu'un nœud nommé node-error-2 colore en rouge chaque ligne qui le mentionne ; json analyse du JSON de style logstash (champs level/message), logfmt analyse le style key=value utilisé par de nombreuses applications Go, le démon Docker et les outils HashiCorp (msg/message, level/lvl/severity, ts/time), gelf analyse du JSON GELF Graylog (niveau syslog numérique), et raw laisse passer les lignes telles quelles. --min-level écarte ensuite tout ce qui est en dessous du niveau choisi, et --grep ne conserve que les lignes dont le message analysé correspond à la regexp.

Les lignes sans niveau détectable passent toujours le filtre --min-level, pour que les stack traces sur plusieurs lignes ne soient pas perdues. Les mêmes valeurs par défaut peuvent être définies une fois pour toutes dans la section logs: de la configuration (les options l'emportent).

Suivi malgré le remplacement du conteneur. Avec -f sur une cible service ou service.slot, logs continue de suivre lorsque le conteneur dont il affiche les logs est remplacé par une mise à jour progressive, un redémarrage ou une replanification : il résout à nouveau le conteneur en cours d'exécution du service (le même slot, ou le même nœud pour un service global), se reconnecte automatiquement — comme docker service logs -f — et affiche une ligne d'information atténuée (container replaced; reconnected to <id> on <node>). Il attend jusqu'à ~30 s qu'un remplaçant soit planifié avant d'abandonner, et s'arrête proprement si le service est supprimé. Une simple cible container-id n'a pas de successeur : le suivi s'arrête donc, comme auparavant.

La détection a lieu dans le client : il connaît la topologie grâce au manager du swarm auquel il est déjà connecté — les agents, locaux à leur nœud, ne peuvent pas voir les remplacements à l'échelle du swarm.

Plusieurs sources à la fois. Avec plusieurs cibles, un service à plusieurs réplicas ou --stack <name>, logs suit toutes les sources ensemble : un service désigne tous ses réplicas en cours d'exécution, comme avec docker service logs. Chaque ligne est préfixée par sa provenance — web.2, ou agent@node-3 pour un service global —, complétée pour que les messages restent alignés, et colorée dans un terminal (jamais si NO_COLOR est défini ni dans un pipe). Chaque source gère sa propre reconnexion lors d'un remplacement de conteneur et sa propre détection --log-format auto, car chaque service journalise à sa façon ; les lignes sont fusionnées entières, jamais coupées entre deux sources. Une source en échec le signale dans ses propres lignes sans arrêter les autres ; le code de sortie en rend compte à la fin. Une cible correspondant à un seul conteneur s'affiche exactement comme avant, sans préfixe.

Les lignes sont fusionnées dans leur ordre d'arrivée, sans tri chronologique entre sources — ajoutez -t quand l'ordre entre services compte. Chaque source est un flux ouvert vers l'agent de son nœud et compte dans la limite -max-streams de cet agent.
$ swarmexec logs -f --tail 100 web $ swarmexec logs --since 15m -t web $ swarmexec logs --log-format json --min-level warn web $ swarmexec logs --log-format auto --min-level warn web # laisser les lignes décider $ swarmexec logs --grep 'timeout|refused' -f web $ swarmexec logs -f api worker db $ swarmexec logs -f --tail 20 --stack shop
Détection du format. --log-format auto — comme a dans la vue des logs de la TUI — confronte les lignes elles-mêmes à chaque format intégré et retient le premier, du plus spécifique au plus général, qui explique au moins deux lignes sur trois. GELF est testé avant JSON, car toute ligne GELF est aussi du JSON valide ; une ligne key=value ne compte comme logfmt que si elle contient une clé msg ou level, ce qui écarte les query strings d'URL et les logs d'accès. L'échantillon porte sur les lignes les plus récentes, pas sur les premières, qui sont la bannière de démarrage d'un framework plutôt que l'application. Quand l'échantillon est trop petit ou trop hétérogène, la détection le signale et conserve la valeur par défaut au lieu de deviner : un mauvais format est pire que pas de format, car --min-level sur un flux mal analysé ne filtre rien. En sortie de pipe, les premières lignes sont retenues jusqu'au verdict (40 au plus, une seconde au plus), pour que la sortie ne soit jamais affichée sous deux formes. Reste à venir : la détection par service à partir d'un catalogue en ligne indexé par image — le même point d'extension, une autre source pour la réponse.

Partage des connexions ssh

Avec un contexte ssh://, swarmexec passe deux fois par ssh pour atteindre le cluster : l'API du manager Docker via le helper de connexion de ssh, et l'agent de chaque nœud via son propre tunnel vers le même hôte. Chaque exec, chaque flux de logs, chaque redirection de port, chaque relevé de statistiques et chaque cycle de rafraîchissement ouvrait jusqu'ici une nouvelle connexion ssh — une poignée de main TCP, un échange de clés et une authentification par connexion, et autant par hôte de rebond — vers un bastion auquel on venait de se connecter un instant plus tôt.

swarmexec leur fait désormais partager un seul transport, à l'aide du ControlMaster d'OpenSSH : la première connexion vers une destination l'ouvre, et chacune des suivantes devient un canal au sein de celui-ci. Mesuré sur un cluster de trois nœuds derrière un hôte de rebond, swarmexec doctor est passé de 8 authentifications et 3,6 s à 2 et 1,0 s. Le trafic lui-même ne change pas, et le gain augmente avec l'activité d'une session.

  • Les sockets de contrôle se trouvent dans $XDG_RUNTIME_DIR/swarmexec/ssh/ (à défaut, dans votre répertoire de cache), créé en 0700 — un socket de contrôle est une session authentifiée active : il reste donc dans votre propre arborescence, jamais dans /tmp.
  • Un socket par destination et route : deux contextes atteignant le même manager par des hôtes de rebond différents ne partagent rien, car il ne s'agit pas de la même connexion.
  • La connexion partagée survit à la commande pendant 60 s, ce qui rend la suivante peu coûteuse, puis se ferme d'elle-même. Ensuite, plus aucun processus de swarmexec ne garde de connexion ouverte.
  • Un socket laissé par un processus maître tué brutalement est sans danger : ssh constate qu'il est mort et ouvre une connexion ordinaire à la place.
  • Indisponible sous Windows, dont OpenSSH n'implémente pas le partage de connexions. Partout ailleurs, SWARMEXEC_SSH_MULTIPLEX=0 le désactive — bon à savoir si vous configurez vous-même ControlPath, car le réglage de swarmexec est passé sur la ligne de commande ssh et prime donc sur ~/.ssh/config.

Onglet Stacks/Services

L'onglet 1, autrefois intitulé Containers. C'est un arbre unique, stack → service → conteneur, qui regroupe exec, les logs, la redirection de ports, l'inspection et les éditeurs de service.

Vérification de version de :latest. Swarm épingle :latest sur un digest au moment du déploiement : un service tagué :latest exécute donc en réalité une image fixe. swarmexec fait la résolution auprès du registre (avec vos identifiants docker locaux) et annote la ligne du service juste après l'URI de l'image : la véritable version entre parenthèses — lue depuis le label org.opencontainers.image.version de l'image — et une flèche vers le haut ↑ lorsque le :latest actuel du registre est un digest plus récent que celui sur lequel le service est épinglé (p. ex. nginx:latest (1.4.0) ↑). Sans garantie et mis en cache : une erreur de registre laisse simplement la ligne sans annotation. La section IMAGE de la surcouche d'inspection affiche la même version et, lorsqu'une image plus récente existe, une ligne sélectionnable newer version available — placez-vous dessus et appuyez sur u (ou Enter) pour mettre à jour le service.

Définir une version avec u — pas seulement quand une mise à jour existe. u ne dépend pas de la présence d'une mise à niveau. La touche est disponible dans toute inspection de service dont swarmexec a pu lire les tags d'image auprès du registre — aussi bien pour un service épinglé sur une version que pour un service sur :latest — et depuis n'importe quelle ligne de la surcouche : vous n'avez jamais à chercher l'indication. Redéfinir la même version, épingler ce qui tourne actuellement ou revenir à un tag plus ancien sont des usages tout à fait normaux ; inutile d'attendre qu'une mise à niveau existe. Le libellé du pied de page indique dans quelle situation vous êtes : u update version lorsqu'une version plus récente a été trouvée (la ligne newer version available est alors présente aussi, avec une cible concrète), et u set version sinon.

Ce qu'ouvre u dépend de ce que sait le registre. Sur un service épinglé sur une version pour lequel une version plus récente existe, c'est le sélecteur de version : un champ dont l'autocomplétion propose les tags plus récents de la même famille, le plus élevé en premier, et qui est prérempli avec celui-ci. Sur un service déjà au tag le plus récent, c'est le même sélecteur, à ceci près que les suggestions portent sur tous les tags listés par le dépôt (prérempli avec le tag en cours d'exécution) — c'est ainsi que l'on épingle une version ou que l'on revient en arrière. Un service sur :latest a lui aussi droit au sélecteur, avec tous les tags connus : y choisir une version concrète permet de faire passer un service :latest du tag flottant à une version épinglée — exactement la correction que demande le constat unpinned-image (voir la surcouche des risques de sécurité plus bas). Seule exception : un service :latest dont une mise à jour de digest est en attente garde sa simple confirmation sur le nouveau digest du registre, comme toujours, car un sélecteur inviterait à y saisir latest, qui se résout en tag nu et supprimerait silencieusement l'épinglage par digest que la mise à jour sert justement à rafraîchir.

Dans le sélecteur, la liste de suggestions est limitée à 25 entrées (un dépôt très actif peut en lister des centaines) et le champ reste en saisie libre : vous pouvez saisir n'importe quel tag existant, y compris un tag plus ancien pour épingler une version ou revenir à une release éprouvée. Un tag saisi est vérifié auprès du dépôt (un tag que celui-ci ne liste pas est rejeté), et choisir un tag plus ancien affiche un avertissement de rétrogradation avant application. Dans tous les cas, la modification est un seul ServiceUpdate / une seule mise à jour progressive, après confirmation. Si le registre n'a renvoyé aucun tag et qu'aucune cible concrète n'est disponible — registre privé ou injoignable, ou service épinglé par digest — vous obtenez un message explicatif, et rien n'est modifié.

Tous les services sont affichés (même ceux ramenés à zéro réplica), chaque ligne se présentant comme une ligne de docker service ls — nom, mode, nombre de tâches en cours/souhaitées, image et ports publiés — et colorée selon l'état réel du service : le rapport en cours/souhaité donne la couleur de base (aqua = toutes les tâches actives, orange = partiel, rouge = arrêté, gris = ramené à zéro), et un healthcheck en échec prend le dessus (voir plus bas). Un marqueur ▸/▾ indique si un service est replié ou déplié ; ses conteneurs en cours d'exécution s'affichent en dessous. Un service en pleine mise à jour progressive porte un badge coloré sur sa ligne dans l'arbre — ⟳ updating ou ↺ rolling back — et le même statut apparaît dans la surcouche d'inspection du service ; il disparaît dès que la mise à jour est terminée.

Un job se mesure à ce qu'il a terminé, pas à ce qui tourne. Un replicated-job ou un global-job n'a pas vocation à rester actif : sa ligne affiche donc terminées/total au lieu de en cours/souhaitées. Un job allé jusqu'au bout s'affiche en 3/3 aqua, là où il apparaissait auparavant en 0/1 rouge — l'affichage d'une panne pour un service qui a fait exactement ce qu'on attendait de lui. Swarm rapporte le nombre souhaité d'un replicated job comme son MaxConcurrent, ce qui explique que le décompte en direct ne dise plus rien d'utile une fois le job terminé. La ligne de stack au-dessus compte le job de la même façon : une sauvegarde nocturne ne fait plus passer toute sa stack à l'orange entre deux exécutions.

Une couleur qui tient compte du healthcheck, pas seulement du nombre de réplicas. La couleur d'une ligne de service venait autrefois du seul rapport en cours / souhaité : un service dont tous les conteneurs échouaient à leur healthcheck s'affichait donc toujours en un paisible 3/3 aqua. Le décompte était exact, mais la ligne trompeuse. L'état des tâches dans Swarm n'aide pas davantage : une tâche reste running alors que son conteneur échoue à chaque sonde — le verdict doit donc venir du nœud. Une sonde en échec est désormais traitée comme une dégradation de même nature qu'un réplica manquant :

  • tous les conteneurs contrôlés en échec (unhealthy) → la ligne passe au rouge : c'est aussi grave que si aucun ne tournait ;
  • certains en échec → orange, comme un déploiement partiel ;
  • tous sains → la ligne garde, inchangée, la couleur que lui donnait déjà le nombre de réplicas ;
  • conteneurs sans healthcheck déclaré → la ligne n'est pas recolorée du tout. On ne sait rien d'eux, et deviner serait la même erreur dans l'autre sens.

Les marqueurs. Une ligne de service porte ✖ N unhealthy en rouge, ou ◌ N starting en jaune tant que les sondes n'ont pas encore réussi ; une feuille de conteneur porte ✖ unhealthy / ◌ starting. Unhealthy prime sur starting : c'est l'état qui demande d'agir. Une ligne de stack agrège ce même marqueur sur tout ce qu'elle contient (voir Regroupement par stack plus bas). Un conteneur sain ne reçoit aucun marqueur, pas plus qu'un conteneur sans healthcheck — le marqueur garde ainsi tout son sens. Ces marqueurs côtoient les marqueurs de ressources cpu/mem décrits ci-dessous, et la santé vient en premier sur la ligne : c'est elle qui contredit le décompte affiché juste à côté.

D'où vient le verdict — et ce qu'il coûte. Rien de plus : il arrive avec les relevés de ressources décrits ci-dessous — même agent, même appel, aucune requête d'API supplémentaire. La liste de conteneurs que l'agent récupère déjà à chaque passe d'échantillonnage porte le verdict dans sa ligne de statut (Up 3 days (healthy)), la chaîne même qu'affiche docker ps. L'analyse est volontairement stricte : tout ce qu'elle ne reconnaît pas devient pas de verdict plutôt qu'une supposition ; si le démon reformule un jour cette ligne, swarmexec cesse donc de prétendre savoir au lieu de déclarer sain un conteneur en échec. Même prérequis que pour les chiffres d'utilisation : il faut des agents de cette release ou plus récents ; un cluster dont les agents n'ont pas été redéployés n'affiche donc aucun marqueur de santé tant que vous ne les avez pas déployés avec swarmexec init --force.

Marqueurs CPU et mémoire en direct. À côté de ces badges, une ligne peut aussi indiquer ce qu'elle consomme réellement à cet instant — jusqu'ici, swarmexec ne pouvait montrer que ce que l'ordonnanceur avait réservé (voir l'onglet Nodes plus bas). Un conteneur — ou un service — dont l'utilisation dépasse 70 % reçoit un marqueur orange, et au-delà de 90 % un marqueur rouge, en fin de ligne : la ressource écrite en toutes lettres (cpu ou mem) suivie du pourcentage (cpu 94 %, mem 91 %). Si les deux sont sous tension, les deux apparaissent. Des mots plutôt que des symboles, et de largeur égale : un marqueur dont il faut chercher la signification ne remplit pas son rôle, et des lettres s'affichent toujours dans un terminal. En dessous de 70 %, rien n'est affiché, pour que les marqueurs restent un signal et ne deviennent pas un simple décor. Une ligne de service reprend le pire de ses réplicas, pas la moyenne — une moyenne masque justement le conteneur sur le point de tomber, celui qu'il faut voir. (La mémoire absolue d'une ligne de service est la somme sur les réplicas ; le pourcentage est le pic.)

Des pourcentages de quoi ? Chacun est calculé par rapport à ce que le conteneur a réellement le droit d'utiliser : sa propre limite lorsqu'il en a une, sinon la capacité du nœud. Toute la différence est là — 91 % d'une limite de 256 Mo signifie qu'un OOM kill est imminent, 91 % d'un nœud de 64 Go est une tout autre histoire. La vue stats de la surcouche d'inspection affiche, par conteneur, les deux termes de cette division et indique la base de calcul sous le tableau.

D'où viennent les chiffres — et pourquoi ils arrivent avec un décalage. L'utilisation ne figure pas dans l'API du manager : les statistiques des conteneurs sont propres à chaque nœud. Elles proviennent d'un RPC de l'agent local au nœud (Stats) ; chaque agent échantillonne ses propres conteneurs en arrière-plan et répond depuis sa mémoire, si bien que le client se contente de l'interroger au rythme du cycle de rafraîchissement qu'il a déjà. Deux conséquences à connaître. Un pourcentage de CPU est un delta entre deux relevés : il n'existe donc pas tant que l'agent n'en a pas effectué deux (quelques secondes) — d'ici là, les vues affichent …, jamais 0% ; la mémoire n'a besoin d'aucun delta et apparaît dès le premier relevé. Par ailleurs, un agent n'échantillonne que tant que quelqu'un regarde : il s'arrête environ une minute après la dernière requête et oublie ses relevés plutôt que d'en servir de périmés. Les tout premiers chiffres mettent donc un instant à apparaître après l'ouverture de l'interface. C'est voulu — un agent que personne ne consulte ne doit rien coûter.
Aucun marqueur nulle part ? Vérifiez la version des agents. L'utilisation est une information complémentaire, qui se dégrade sans bruit : un nœud dont l'agent est injoignable — ou antérieur à cette release, et qui ne connaît donc pas le RPC Stats — ne fournit tout simplement aucun relevé. Les marqueurs restent éteints, le bloc du nœud est absent et tout le reste fonctionne normalement ; le client cesse en outre d'interroger ce nœud pendant un moment au lieu de le sonder à chaque rafraîchissement. Sur un cluster dont les agents n'ont pas encore été redéployés, il n'y a donc aucun chiffre d'utilisation ni aucun marqueur de santé tant que les agents ne sont pas à jour — déployez-les avec swarmexec init --force. C'est de loin la raison la plus probable si vous ne voyez rien.

Regroupement par stack. docker stack deploy pose sur chaque service qu'il crée le label com.docker.stack.namespace. swarmexec lit ce label dans la spec du service que le manager a déjà renvoyée — Swarm n'a aucun objet « stack », ce label est le seul lien — et organise l'arbre sur trois niveaux : stack → service → conteneur. Une ligne de stack affiche le nom de la stack, le nombre de services qu'elle contient et le nombre de tâches en cours/souhaitées, cumulé ((3 svc · 7/8)), coloré selon exactement la même règle qu'une ligne de service : le total en cours / souhaité, avec la même prise en compte du healthcheck par-dessus. Viennent ensuite les compteurs agrégés, lorsqu'ils ne sont pas nuls : ⟳ n — les services de cette stack en pleine mise à jour progressive —, 🛡 n — les services présentant un constat de sécurité qui mérite une action, le même bouclier que portent les lignes de service — puis le marqueur de santé, ✖ N unhealthy ou ◌ N starting, cumulé sur tous les conteneurs de tous les services de la stack. Même repliée, une stack indique donc si quelque chose à l'intérieur demande votre attention. C'est d'ailleurs là que la remontée de l'état de santé compte le plus : la ligne de stack est le niveau qu'un opérateur parcourt en premier ; un « tout fonctionne » trompeur y est donc plus grave qu'un niveau plus bas, et non moins.

Les services créés avec docker service create ne portent pas de label de stack ; ils sont regroupés sous (no stack), toujours trié en dernier pour ne jamais repousser les vraies stacks vers le bas de la liste. Rien n'est masqué : chaque service apparaît toujours exactement une fois. Les stacks sont triées par nom et s'affichent dépliées, si bien que l'arbre groupé montre les mêmes services que la liste à plat ; les éléments que vous repliez le restent après le rafraîchissement automatique.

Le regroupement est actif par défaut, mais ne s'applique que si au moins un service du cluster porte réellement un label de stack — sur un cluster sans stacks, l'arbre reste exactement tel qu'il a toujours été, sans parent (no stack) inutile. s bascule entre l'arbre groupé et la liste à plat des services (le pied de page l'indique sous la forme s stacks) ; en l'absence de tout label de stack, un message le signale plutôt que de redessiner un arbre identique. La touche est réaffectable via stack_group dans keys.yaml.

La recherche (/) ne change pas : le filtre porte toujours sur le service, le conteneur et le nœud. Une stack que le filtre vide disparaît de l'arbre, et les compteurs de chaque ligne de stack décrivent ce qui s'y trouve réellement — ils suivent donc le filtre au lieu d'annoncer des services que vous avez exclus.

Le menu d'actions propose logs, bash, sh, shell as user… (demande un utilisateur/UID, comme docker exec -u, pour les images dont l'utilisateur par défaut n'a pas les outils ou les droits nécessaires) et port forward (les shells indisponibles sont grisés après vérification). Dans la barre de recherche, Enter conserve le filtre et revient à la liste ; Esc efface le filtre et ferme la barre.

Risques de sécurité (!). À chaque récupération de la liste des services, swarmexec exécute un ensemble de petits analyseurs statiques sur la spec de chaque service — la spec que le manager a déjà renvoyée : aucun appel d'API supplémentaire, aucune intervention de l'agent, et rien n'est exécuté dans vos conteneurs. Un service présentant un constat qui mérite une action est marqué d'un 🛡 en tête de sa ligne dans l'arbre des services, dans une colonne de largeur fixe devant le nom, de sorte que les boucliers s'alignent verticalement et se repèrent d'un coup d'œil. Appuyez sur ! pour ouvrir la surcouche des risques de sécurité, et sur w à l'intérieur pour écrire un rapport Markdown sur tout le cluster — qui couvre davantage que la surcouche, puisqu'il ajoute les contrôles relevant du cluster et non d'un service.

Huit sont classées high, chacune signalée avec sa raison : ALL (accorde toutes les capabilities), SYS_ADMIN (quasi root : contrôle des montages, des namespaces et des cgroups), SYS_MODULE (peut charger des modules noyau), SYS_PTRACE (peut inspecter et contrôler d'autres processus), SYS_RAWIO (accès d'E/S brut aux périphériques), DAC_READ_SEARCH (contourne les contrôles de permission en lecture), NET_ADMIN (contrôle total du réseau du nœud), NET_RAW (peut forger et capturer des paquets bruts). Toute autre capability ajoutée est medium — un privilège qui dépasse l'ensemble par défaut. Un constat par capability ajoutée ; les deux écritures sont reconnues, sans tenir compte de la casse (CAP_SYS_ADMIN et SYS_ADMIN)
host-network — « runs on the host network »highle service est attaché au réseau nommé host : le conteneur partage la pile réseau du nœud, il n'y a donc plus d'isolation réseau et la publication de ports de swarm ne s'applique plus. Il peut joindre tout ce que le nœud peut joindre — y compris les services qui n'écoutent que sur localhost, que l'on croit d'ordinaire hors de portée d'un conteneur
unconfined — « seccomp disabled » / « AppArmor disabled »highle sandboxing au niveau du noyau a été désactivé pour le conteneur : seccomp réglé sur unconfined — le conteneur peut effectuer n'importe quel appel système, ce qui lève la principale barrière contre les exploits du noyau — ou confinement AppArmor désactivé. Les deux sont signalés séparément : un service qui désactive les deux reçoit deux constats
root-user — « runs as root »highla spec fait tourner le conteneur explicitement en root — User=root ou l'UID 0 (les formes numériques comme 00 ou +0 sont aussi détectées ; seule la partie utilisateur de user:group est examinée)
secret-in-env — « secret in environment variable »highune variable d'environnement dont le nom évoque un identifiant contient une valeur en clair dans la spec du service, lisible par quiconque peut lire la spec. Utilisez plutôt un secret Docker ou la convention *_FILE
root-user — « no user set »lowaucun utilisateur n'est défini : le conteneur s'exécute donc sous l'utilisateur par défaut de l'image, souvent root. Purement informatif, et ne marque pas le service : l'absence d'utilisateur est la situation par défaut de presque tous les services Swarm, et savoir s'il s'agit réellement de root dépend du USER de l'image, que la spec du manager ne révèle pas
no-resource-limits — « no resource limits »lowla tâche ne fixe ni limite CPU ni limite mémoire : un conteneur qui s'emballe peut accaparer tout le nœud et priver de ressources tout ce qui s'y exécute. Purement informatif — voir ci-dessous
unpinned-image — « image not pinned »lowl'image est épinglée sur :latest, ou ne porte aucun tag (ce qui revient à :latest) — la version exécutée peut changer sans que la spec change, un déploiement n'est donc pas reproductible. Une image épinglée par digest (…@sha256:…) est parfaitement reproductible et n'est jamais signalée, et le deux-points du port d'un hôte de registre (registry:5000/img) n'est pas pris pour un tag. Purement informatif — voir ci-dessous

Pourquoi les contrôles informatifs ne marquent jamais un service. Seul un constat plus grave que low — high ou medium — appelle une action sur un service et place le 🛡 sur sa ligne dans l'arbre. Les constats low (no-resource-limits, unpinned-image et le « no user set » de root-user) concernent presque tous les services d'un cluster réel : les signaler mettrait un bouclier sur presque chaque ligne et détruirait précisément le repérage en un coup d'œil qui justifie le marqueur. Ils ne sont pas escamotés pour autant — dès qu'un service est marqué pour autre chose, ses constats low sont listés avec les autres dans la surcouche, là où ils valent vraiment la peine d'être lus.

Aucune valeur de secret n'est jamais affichée. Des huit contrôles, seul secret-in-env examine les variables d'environnement, et son constat ne nomme que la clé de la variable ; sa valeur n'est jamais reprise dans le constat, jamais affichée et jamais copiée. Le contrôle est aussi conçu pour éviter les faux positifs : il compare des segments entiers délimités par _ (PASSWORD, PASSWD, PASS, PASSPHRASE, SECRET, TOKEN, APIKEY, CREDENTIAL(S), PRIVATEKEY, ainsi que les paires API_KEY, ACCESS_KEY, PRIVATE_KEY, SECRET_KEY, CLIENT_SECRET, AUTH_TOKEN), si bien que COMPASS, PASSENGER_PORT ou BYPASS_AUTH ne sont pas signalés. Les clés qui ne font que désigner un identifiant sont exemptées (_FILE, _PATH, _URL, _URI, _NAME, _ID, _TYPE, _ENABLED, _REQUIRED, _LENGTH, _TIMEOUT, _TTL, _EXPIRY, _ALGORITHM), tout comme les valeurs qui ne peuvent manifestement pas être un identifiant : un chemin absolu, un booléen, un nombre.

La surcouche liste chaque service signalé (« N of M service(s) flagged · 8 checks »), regroupés par service, chaque constat sur sa propre ligne avec une pastille de gravité — ● high, ● medium, ● low — un titre court et une explication d'une ligne. Les constats sont triés du plus grave au moins grave. Dès qu'un service est signalé pour un problème appelant une action, ses constats informatifs de niveau low sont listés eux aussi. Si le service sous le curseur en fait partie, il est présélectionné et affiché à l'écran. Quand rien n'est signalé, la surcouche le dit explicitement et nomme chaque contrôle exécuté (« Checked: Docker socket mounted in, added Linux capabilities, host network, seccomp / AppArmor disabled, container user, secrets in environment variables, missing resource limits, unpinned image. »), de sorte que le feu vert indique aussi ce qu'il couvre ; si la liste des services n'est pas encore chargée, elle indique que rien n'a encore été analysé plutôt que de donner un faux feu vert. j/k font défiler, Esc (ou q, ou à nouveau !) ferme.

L'analyse repose sur un registre extensible d'analyseurs, pas sur une liste figée : un nouveau contrôle apparaît automatiquement à la fois dans le marqueur de l'arbre et dans la surcouche. Le texte de la surcouche provient lui aussi de ce registre : le nombre de contrôles de son en-tête et la liste « Checked: » sont générés à partir des analyseurs eux-mêmes et ne peuvent donc pas diverger de ce qui a réellement été exécuté, contrairement à une liste codée en dur. La touche est réaffectable sous le nom security_risks dans keys.yaml.

i ouvre une surcouche d'inspection pour l'élément sous le curseur — sur un service, elle affiche docker service inspect ; sur une feuille conteneur, l'inspection de la tâche swarm (la vue qu'a le manager de cette instance : état, slot, nœud, id du conteneur, spec du conteneur, ressources et historique des états). Les deux proviennent du manager du swarm. La surcouche s'ouvre sur un résumé sous forme de tableau, pensé pour l'opérateur, avec des sections classées par pertinence opérationnelle — réseaux, labels, volumes/montages et secrets (et configs) d'abord, puis ports, image, mode, env, ressources, placement et politique de mise à jour (plus l'état, le nœud et l'id du conteneur pour un conteneur/une tâche), les ids et horodatages venant en dernier. La première ligne de la surcouche, à l'intérieur de la bordure et fixée au-dessus du contenu qui défile, est une barre d'onglets qui nomme ses trois vues — table 1   stats 2   raw json 3 —, la vue courante étant dans la couleur d'accentuation ; elle reprend la forme de la barre d'onglets de la fenêtre principale : un libellé suivi du chiffre qui le sélectionne. 1, 2 et 3 mènent directement au tableau, aux stats et au JSON brut du démon, et t fait toujours défiler tableau → stats → JSON brut, puis revient au début. L'indication du pied de page se résume à 1-3/t view, et le titre de la bordure ne répète plus le nom de la vue courante — il affiche simplement inspect service foo, puisque la barre indique déjà où vous êtes. Notez que cette vue en tableau est la vue de la tâche côté manager, et non un docker container inspect complet, effectué sur le nœud, du conteneur en cours d'exécution — une véritable inspection de conteneur via l'agent est prévue.

La vue stats. La vue du milieu montre l'utilisation des ressources en direct — les mêmes relevés que ceux qui alimentent les marqueurs de l'arbre : l'ouvrir ne coûte aucun appel supplémentaire, et les chiffres continuent de se rafraîchir tant qu'elle est ouverte. C'est un tableau, avec une ligne par conteneur du service (ou l'unique conteneur d'une inspection de tâche) :

RESOURCE USAGE measured on each node, refreshed with the tree CONTAINER NODE HEALTH CPU MEMORY gl_gitlab.1 docker3v2 healthy 0.07 / 4.00 cores (2%) 6.823GiB / 8GiB (85%) limits are the container's own where it has one, otherwise the node's capacity

Un tableau, parce qu'un pourcentage seul n'est pas lisible si l'on ne sait pas déjà comment l'outil mesure — 94 % de quoi ? Chaque cellule porte ses propres unités : 0.07 / 4.00 cores se passe de légende, et le pourcentage figure à côté de la valeur à laquelle il se rapporte ; et plusieurs réplicas se comparent en parcourant une colonne plutôt qu'en confrontant des blocs empilés. La colonne HEALTH énonce le verdict en toutes lettres : healthy, unhealthy, starting, ou none pour un conteneur qui ne déclare aucun healthcheck. none et healthy sont délibérément deux mots distincts, et non un mot et une case vide : aucun healthcheck configuré et la sonde réussit sont deux faits différents, et une case vide se lirait comme le second. Un conteneur pour lequel aucun agent n'a transmis de relevé — nœud injoignable, agent trop ancien pour le RPC Stats, ou conteneur démarré depuis le dernier relevé — affiche no reading dans les deux colonnes de ressources au lieu d'un zéro, qui se lirait comme « au repos ».

Les dernières minutes. Sous le tableau, chaque conteneur reçoit deux sparklines, CPU et mémoire, sur les derniers relevés — pour distinguer un service qui stagne à 90 % d'un autre qui vient de grimper à 90 %. Les deux utilisent une échelle fixe de 0 à 100 % du même dénominateur que le tableau, si bien que deux conteneurs se comparent directement et qu'un conteneur au repos reste plat. L'historique n'est conservé qu'en mémoire, 15 minutes au plus, et les relevés continuent d'arriver tant que la vue est ouverte. Un blanc est une période sans relevé — un nœud qui n'a pas répondu, un cluster que vous ne regardiez pas —, jamais une chute à zéro.

LAST MINUTES gl_gitlab.1 cpu ▁▁▂▂▁▁▃▇██▇▅▃▂▁ ▁▁▂▂▁▁▁ mem ▆▆▆▆▆▆▇▇▇▇▇▇▇▇▇ ▇▇▇▇▇▇▇ last 9 min share of each container's limit (or its node), oldest left; a blank is no reading, not zero

La note sous le tableau indique le dénominateur : la limite propre du conteneur lorsqu'il en a une, sinon la capacité du nœud. C'est ce qui donne un sens à un pourcentage — 85 % d'une limite de 8 Gio et 85 % d'un nœud de 64 Gio sont deux situations très différentes. La mémoire est exprimée en unités binaires (MiB/GiB), les mêmes que dans le détail des nœuds et que celles qu'utilise docker lui-même : une même valeur ne se lit donc jamais différemment à deux endroits. Lorsque plusieurs conteneurs sont mesurés, une synthèse s'ajoute sous le tableau : CPU et mémoire du pire réplica — et non une moyenne, qui masquerait justement le conteneur sur le point d'être tué par l'OOM killer — ainsi que la mémoire totale de l'ensemble. L'entrée t de la surcouche d'aide ? indique en conséquence cycle table / stats / raw JSON.

La section NETWORKS est repliable, et elle répond à la question « à quelle adresse le joint-on ? » avant même de déplier quoi que ce soit : chaque réseau attaché apparaît sous la forme d'une ligne repliée + <network> 🔒 vip 10.0.5.2/24 (2 dns names). Une icône de cadenas 🔒 après le nom du réseau signale un réseau overlay chiffré (chiffrement du plan de données, --opt encrypted) ; son absence signifie non chiffré. Sur l'inspection d'un service, l'adresse est libellée vip — l'IP virtuelle du service sur ce réseau, celle sur laquelle répond le répartiteur de charge du swarm, tirée du ServiceInspect du manager (Endpoint.VirtualIPs). Sur celle d'un conteneur/d'une tâche, elle est libellée addr : l'adresse propre de ce conteneur sur ce réseau. Un service en mode de point d'accès dnsrr n'a pas de VIP du tout — c'est voulu, ce n'est pas une donnée manquante — si bien qu'au lieu d'une case vide, le réseau déplié affiche la ligne no vip — dnsrr endpoint mode, the DNS name resolves to the containers. Le réseau ingress est lui aussi listé ici, bien qu'aucune spec ne le mentionne jamais — le swarm y attache le service de lui-même (voir plus bas). Il est ajouté après les réseaux déclarés par la spec, jamais intercalé entre eux, et son en-tête se présente ainsi : + ingress vip 10.0.0.250/24 (routing mesh) — la mention (routing mesh) remplace un décompte de noms DNS qui ne pourrait jamais afficher que (0 dns names).

Placez-vous sur une ligne de réseau et appuyez sur Enter pour la déplier ou la replier. Dépliée, elle liste les noms DNS qui pointent vers le service/conteneur sur ce réseau — le nom du service, tasks.<service> et les éventuels alias personnalisés — pour que vous voyiez, réseau par réseau, sous quel nom DNS il est joignable et quels alias il porte. En dessous se trouve une seconde ligne repliable, + 2 containers (au singulier, + 1 container) ; Enter sur celle-ci ouvre le niveau le plus profond : une ligne par conteneur, alignée en colonnes, web.1 10.0.1.5/24 host-a — nom de la tâche, son adresse sur ce réseau, et le nœud sur lequel elle tourne (les tâches répliquées sont nommées <service>.<slot>, les tâches globales, qui n'ont pas de slot, <service>.<node>).

Le filtre porte sur l'état souhaité (desired state) de la tâche, pas sur son état courant : toute tâche que le manager veut encore voir tourner est listée, y compris celles qui ne sont que preparing, assigned ou starting — elles disposent déjà de leur adresse, et pendant une mise à jour progressive, c'est le cas de la plupart ; filtrer sur l'état courant viderait donc le détail précisément quand il est le plus utile. Une tâche que le manager a abandonnée — état souhaité shutdown, c'est-à-dire remplacée par une mise à jour progressive, supprimée par une réduction d'échelle ou en échec — n'est pas listée : son adresse a été libérée et appartient peut-être déjà à un autre conteneur ; l'afficher serait donc carrément faux. Une tâche qui ne reçoit pas encore de trafic affiche son état entre parenthèses en fin de ligne, web.1 10.0.1.5/24 host-a (starting) ; une tâche en cours d'exécution n'a pas de suffixe. Les lignes proviennent d'un TaskList de l'API du manager filtré sur le service, sans garantie : une erreur d'API laisse simplement le détail vide. Les deux niveaux se replient indépendamment ; replier le réseau masque aussi le niveau des conteneurs.

La ligne ingress est celle qui ne figure dans aucune spec : le swarm attache de lui-même un service au réseau ingress dès que ce service publie un port en mode ingress, et cet attachement n'apparaît nulle part dans la spec du service — pourtant, sa vip est l'adresse sur laquelle le routing mesh répond réellement, la première chose que l'on veut savoir quand un port publié se comporte mal. Elle a donc sa propre ligne, ajoutée après les réseaux déclarés par la spec et de forme légèrement différente : aucun nom DNS de service n'est résolu sur ingress ; là où un autre réseau compte ses noms, cet en-tête porte donc la mention (routing mesh). Une fois dépliée, la ligne liste à la place les ports publiés via ingress qui ont amené le service sur ce réseau — la raison d'être de la ligne —, un par ligne : published 2222 -> 22/tcp. Les ports publiés en mode host contournent le routing mesh et n'y sont volontairement pas listés. En dessous, la ligne descend jusqu'aux conteneurs exactement comme toute autre ligne de réseau : le même niveau + 1 container, avec l'adresse propre de chaque conteneur sur le réseau ingress. Un service qui ne publie aucun port en mode ingress n'y a pas de VIP — et n'a donc pas du tout cette ligne.

Un service GitLab publiant SSH sur 2222, les deux niveaux dépliés :

- dbnet vip 10.0.1.137/24 (2 dns names) gl_gitlab tasks.gl_gitlab - 1 container gl_gitlab.1 10.0.1.54/24 docker3v2 - ingress vip 10.0.0.250/24 (routing mesh) published 2222 -> 22/tcp - 1 container gl_gitlab.1 10.0.0.64/24 docker3v2

Une copie dans NETWORKS donne l'adresse sans son masque — 10.0.5.2, la forme que vous collez dans un curl ou un ping : sur une ligne de réseau, sa vip/addr ; sur une ligne de conteneur, l'adresse de ce conteneur. Une ligne de réseau sans adresse (dnsrr) copie le nom du réseau, comme auparavant. Sur les deux types de lignes repliables, Enter déplie/replie ; sur toute autre ligne, il copie (et y copie toujours).

Lorsque vous inspectez un service (et non une feuille conteneur/tâche, dont la surcouche reste en lecture seule), le pied de page de la surcouche propose aussi plusieurs touches d'édition, chacune correspondant à un ServiceUpdate de l'API du manager qui déclenche une mise à jour progressive / une réconciliation des tâches du service.

Commencez par a — le menu d'actions. Dans l'inspection d'un service (et uniquement là), a ouvre une liste unique de tous les éditeurs et actions que propose la surcouche, pour vous éviter de retenir ~14 touches sensibles à la casse (d/D, s/f, p/l/e, n/S/v, r/P, R, X). Chaque entrée affiche sa touche directe devant son libellé : le menu est donc aussi l'endroit où l'on apprend les touches. C'est la voie la plus facile à découvrir, sans touche Maj — et non une version allégée : choisir une entrée ferme le menu et ouvre exactement ce qu'ouvre la touche directe ; les deux sont donc équivalents, et non des variantes au comportement différent. Les entrées, dans l'ordre : update image version… (set image version… quand aucune version plus récente n'a été trouvée — épingler un tag de votre choix ou revenir à un tag antérieur est tout aussi légitime), diff spec (previous → current), roll back to the previous version, placement diagnosis — why a task is missing, scale, force-update, edit ports, edit labels, edit env, edit networks, edit secrets, edit mounts, edit resources, edit placement, remove service — l'action destructive, signalée en rouge — et Cancel. On se déplace avec j/k (g/G vont à la première/dernière entrée), Enter sélectionne ; Esc, ou l'entrée Cancel, ferme le menu sans rien faire. Le sélecteur de version d'image vient en premier, parce que changer de version est la modification de service la plus courante qui soit ; sa touche directe u fonctionne toujours depuis n'importe quelle ligne de l'inspection. Si aucune version ne peut être choisie pour l'image — une référence sans tag, ou un registre qui refuse de lister les tags du dépôt, typiquement un registre privé pour lequel le client n'a pas d'identifiants —, l'entrée reste dans la liste et le signale au lieu de disparaître sans bruit, en renvoyant vers docker service update --image, qui, lui, fonctionne. Barre latérale des contextes

Les clusters occupent une colonne sur le bord droit, et non un onglet. On change de cluster depuis l'endroit où l'on se trouve — et c'est justement la liste des clusters qui indique où l'on se trouve. Elle a donc sa place à l'écran, et non sur une page vers laquelle il faudrait se déplacer.

c lui donne le focus clavier depuis n'importe quel onglet ; un nouvel appui sur c ou Esc le rend à l'onglet où vous étiez. Le cluster actif est marqué ▶ — c'est le nom affiché dans le pied de page. Un cluster déjà visité pendant la session porte un · vert : il est toujours connecté, y revenir est donc instantané. Un cluster qui a refusé la connexion porte un ✗ rouge. Le contexte intégré default est protégé.

La barre latérale s'adapte au nom de contexte le plus long et s'efface sur un terminal étroit : en dessous d'environ 92 colonnes, elle se masque plutôt que de tronquer l'arbre, et réapparaît tant que c lui donne le focus. Les points d'accès ne figurent pas dans la colonne — la place manque, et i en affiche le détail complet.

Changer de cluster préserve votre session. L'UI ne se reconstruit pas : la position du curseur, les stacks et services dépliés et le filtre / sont mémorisés par cluster ; en revenant, vous retrouvez donc tout exactement là où vous l'aviez laissé. Les redirections de port continuent de fonctionner après le changement — l'onglet Forwards comporte une colonne CLUSTER pour voir d'un coup d'œil lesquelles appartiennent au cluster affiché et lesquelles non.

Seul le cluster affiché est interrogé : quand vous passez à un autre, le précédent cesse de se rafraîchir et sa connexion ssh expire d'elle-même peu après. Le premier passage vers un cluster prend le temps de s'y connecter, car la connexion est établie avant que quoi que ce soit change à l'écran — en cas d'échec, le cluster concerné vous est indiqué et vous restez sur celui qui fonctionne. Chaque retour ultérieur est immédiat.

Plibère l'espace disque occupé par les images sur le nœud (P majuscule, c.-à-d. Maj+p — le même geste que pour le prune de l'onglet Volumes). Ouvre un petit menu proposant les deux modes décrits ci-dessous, chacun avec sa propre confirmation ; mieux vaut lire ce que fait chacun avant de choisir. Le pied de page se termine par P reclaim images et la surcouche ? l'affiche sous la forme reclaim image disk space on the node. Réaffectable via node_prune_images

Ressources réservées. Les détails du nœud comportent un bloc reserved by tasks (scheduler's view) : pour le CPU et la mémoire, une barre accompagnée de reserved / capacity et de ce qui reste libre. La barre est verte, passe au jaune à partir de 75 % et au rouge à 100 % ou au-delà ; la surréservation est signalée en toutes lettres, et la valeur « libre » n'est jamais négative. Un nœud qui n'annonce aucune capacité le signale au lieu d'afficher une barre. Le bloc ne coûte aucun appel d'API supplémentaire — la liste des nœuds récupère déjà la liste des tâches.

Ce sont des réservations, pas une consommation. Les chiffres sont la somme des Reservations déclarées par les tâches — exactement le calcul que fait l'ordonnanceur du swarm lui-même pour décider si une tâche tient sur un nœud, et la raison habituelle pour laquelle un service reste non planifiable. La consommation réelle de CPU/RAM est propre au nœud et n'est pas ce qui est affiché ici : elle a son propre bloc, juste en dessous. Les tâches qui ne déclarent aucune réservation sont comptées et signalées à part : elles ne réservent rien ici mais peuvent tout de même accaparer le nœud entier ; un faible pourcentage ne signifie donc pas que le nœud est inactif — et dans la plupart des clusters, rares sont les services qui définissent des réservations. Une tâche conserve sa réservation de son affectation jusqu'à ce qu'elle atteigne un état final : les tâches preparing ou starting comptent donc, tandis que les tâches shutdown / failed / complete / rejected ne comptent pas (le swarm les garde dans la liste des tâches à titre d'historique).

Utilisé par les conteneurs. En dessous figure un second bloc — in use by containers (measured on the node) — avec les mêmes barres proportionnelles : ce que les conteneurs du nœud consomment réellement à cet instant, le CPU en cœurs et la mémoire, chacun rapporté à la capacité du nœud. Les deux blocs sont volontairement séparés, car ils répondent à des questions différentes et divergent souvent fortement : un nœud peut être entièrement réservé et inactif, ou à peine réservé et saturé. Les chiffres proviennent de l'agent du nœud, la même source que les marqueurs d'utilisation de l'arbre des services — tant que le delta CPU n'est pas disponible, la ligne affiche measuring…, et un nœud dont l'agent est injoignable ou trop ancien n'a pas de bloc du tout, plutôt qu'une rangée de zéros qui se lirait comme « inactif ».

Les conteneurs uniquement. Seuls les conteneurs du nœud sont comptés — le noyau, le démon docker et tout ce qui tourne en dehors de docker ne sont pas inclus dans ce chiffre. Ce n'est pas la charge système du nœud, et le bloc le précise lui-même.

Images sur ce nœud. En dernier, les détails comportent un bloc images on this node : le volume occupé par le magasin de couches du nœud et le nombre d'images, puis la part récupérable en restes sans tag (un nœud sans image non taguée l'indique, plutôt que d'afficher un zéro). Lorsqu'il y en a, une ligne supplémentaire indique l'espace occupé en plus par des images taguées mais inutilisées — présenté comme un coût, les supprimer oblige à retélécharger ces images, et non comme une proposition. Ce bloc existe parce que les images sont la seule ressource locale au nœud que le niveau cluster ne voit pas du tout : l'API du manager n'a aucune visibilité sur les images, contrairement aux volumes, dont elle sait au moins qu'ils sont montés. Les volumes se géraient déjà à l'échelle du cluster depuis swarmexec ; un nœud dont le disque se remplissait discrètement de vieilles couches n'était même pas visible. Le bloc se charge séparément, en parallèle de la liste des nœuds, et apparaît donc un instant après le reste de la surcouche.

Libérer l'espace — P sur l'onglet Nodes. Le menu qui s'ouvre comporte deux entrées — délibérément, et non une action avec une case à cocher —, car ce sont deux actes différents et une case à cocher expose à choisir par mégarde le mode destructeur :

EntréeCe qu'elle supprime
untagged leftoversles couches laissées par les rebuilds, à partir desquelles rien ne peut démarrer. Sans risque : cela ne peut ni arrêter un service ni forcer un pull
every unused imagesupprime en plus les images taguées qu'aucun conteneur n'exécute à cet instant. Sur un nœud swarm, cela inclut tout service actuellement ramené à zéro réplica et toute tâche entre deux redémarrages — chacun devra retélécharger son image
Ne lisez pas la seconde entrée comme « la même chose, en plus large ». « Every unused image » supprime des images qui appartiennent à quelque chose qui, simplement, ne tourne pas à cet instant : un service ramené à zéro, une tâche en train de redémarrer, une stack arrêtée la veille. Tous perdent leur image et doivent la retélécharger pour redémarrer — et si le registre est injoignable, ils ne redémarreront pas. Chacune des deux entrées passe par sa propre boîte de confirmation, qui énonce exactement cette conséquence et indique le nombre d'octets qu'elle libérerait ; ce sont deux textes distincts, précisément pour qu'aucun ne finisse par décrire l'autre.

Deux modes, deux autorisations. L'agent les autorise comme deux actions distinctes — image.prune pour les restes sans tag et image.prune.all pour le nettoyage complet — si bien qu'une politique peut autoriser la récupération des couches sans tag sans autoriser le mode destructeur. Chaque prune est inscrit dans le journal d'audit de l'agent avec le mode utilisé, l'espace libéré et le nombre d'images supprimées.

D'où viennent les chiffres. Ils proviennent de la même source que docker system df, et concordent exactement avec lui — vérifié sur un nœud réel : 56 images, 32,70 Go sur disque, 22,99 Go récupérables. En particulier, swarmexec n'additionne pas les tailles individuelles des images : la taille d'une image inclut toutes les couches qui la composent, et les couches sont partagées — cette somme surestime donc fortement ; pendant le développement, elle annonçait 32,7 Go là où le démon indiquait 22,2 Go. Une réserve à signaler : le chiffre restes sans tag uniquement est une borne inférieure — une couche partagée par deux images sans tag n'entre dans la taille propre d'aucune des deux — si bien qu'un prune des images sans tag peut libérer un peu plus qu'annoncé, jamais moins.

Même prérequis que pour les chiffres d'utilisation et de santé ci-dessus : il faut des agents de cette release ou plus récents. Un nœud dont l'agent est plus ancien n'affiche tout simplement aucun bloc images, et indique qu'il n'a pas répondu si vous appuyez sur P — déployez les agents avec swarmexec init --force.

Onglet Configs

Onglet 7 — le pendant de l'onglet Secrets pour l'autre type d'objet que le swarm distribue aux conteneurs, avec une différence décisive : le contenu d'une config est lisible. L'onglet Secrets ne peut jamais afficher de valeur (l'API Docker ne la renvoie pas) ; le détail d'une config affiche son contenu réel, si bien que vous voyez ce qu'un service reçoit vraiment sans recourir à docker config inspect. C'est tout l'intérêt de cet onglet.

La liste est en lecture seule : CONFIG (nom), USED BY (nombre de services qui la montent), SIZE, AGE, UPDATED et LABELS (nombre).

ToucheAction
Enter / iouvre la surcouche de détail : nom, id, taille, création, mise à jour, services qui la montent, labels — et le contenu de la config
j k / g Gdans la surcouche de détail : défilement · début / fin (Esc ferme)

Le contenu est récupéré à la demande, à l'ouverture de la surcouche — et non avec la liste — car une config peut être un nginx.conf entier ; en attendant, la surcouche affiche loading…, et une config vide indique (empty). Ce qui s'affiche est un aperçu, limité à la fois à 64 Kio et à 500 lignes. Les deux limites sont nécessaires : ne limiter que les octets permettrait encore à un fichier de lignes très courtes de produire des dizaines de milliers de lignes à l'écran — chacune indentée —, et c'est précisément ce qui fait ramer la vue. Une troncature est toujours signalée (« … truncated at 500 lines », ou à la limite d'octets), jamais silencieuse, et un contenu binaire est signalé, pas déversé à l'écran (« (binary content, N — not shown) », détecté par la présence d'octets NUL au début des données). La config complète n'est qu'à un docker config inspect.

USED BY est calculé exactement comme dans l'onglet Secrets : le swarm ne tient aucun index inverse d'une config vers ses utilisateurs ; swarmexec lit donc les specs des services (un ServiceList) et reconnaît une référence à l'ID ou au nom de la config — une spec peut utiliser l'une ou l'autre forme, les deux sont donc recherchées et fusionnées. Sans garantie : si la liste des services ne peut pas être lue, les configs s'affichent quand même, simplement sans cette correspondance.

Dans un shell intégré, Ctrl-] détache la session (sans terminer le processus). La vue des logs — d'un seul conteneur, ou les logs agrégés d'un service — offre la même analyse et le même filtrage selon le format que la commande logs :

La vue réaffiche immédiatement les lignes en tampon quand vous changez de format, de niveau ou de grep, et la barre de titre affiche les réglages actifs fmt:… lvl:… grep:….

En mode suivi, la vue des logs se reconnecte lors du remplacement d'un conteneur, de la même façon que la commande logs — aussi bien pour les logs d'un seul conteneur que pour les logs agrégés d'un service (chaque réplica étant suivi par slot). Les messages de reconnexion s'affichent directement dans la vue des logs.

Visualiseur de logs

Appuyez sur ` (accent grave) depuis n'importe quel onglet pour afficher ou masquer une surcouche de logs en direct. Elle présente les entrées les plus récentes du tampon circulaire en mémoire — les plus récentes en bas —, se rafraîchit tant qu'elle est ouverte et colore chaque entrée selon son niveau (rouge = error, jaune = warn, gris = debug). ↑/↓ font défiler ; Esc, q ou ` la ferment. C'est la fenêtre de la TUI sur les logs qui vont aussi dans le fichier de log, puisque le terminal lui-même ne peut pas les afficher pendant que l'UI occupe l'écran.

Réactivité. La liste des conteneurs se rafraîchit en dehors du thread de l'UI (ses deux appels à l'API du manager s'exécutaient auparavant de façon synchrone et pouvaient figer brièvement la TUI), et un watchdog en arrière-plan journalise un avertissement quand la boucle d'événements se bloque — pratique pour diagnostiquer une lenteur depuis le visualiseur de logs.

Touches personnalisées

Les raccourcis clavier sont réaffectables dans ~/.config/swarmexec/keys.yaml (à côté de config.yaml ; remplacez le chemin avec $SWARMEXEC_KEYS). Chaque valeur est une seule touche, ou le mot space. Les touches structurelles — Enter, Esc, Tab, les flèches, les touches de numéro d'onglet 1–9 et les équivalents vim j/k/g/G — sont fixes. Le pied de page affiche toujours les touches effectivement configurées, et la surcouche ? les liste toutes.

# ~/.config/swarmexec/keys.yaml — omettez une ligne pour garder la valeur par défaut quit: q refresh: r copy: y toggle_mouse: m search: / fold: h unfold: l forward: p container_inspect: i logs: L security_risks: "!" # "!" doit être entre guillemets — YAML stack_group: s volume_select: space volume_select_all: a volume_delete: d volume_prune: P volume_used_by: i volume_attach: A volume_sort: s volume_sort_reverse: S volume_new: n network_attached: i network_new: n context_use: u context_new: n context_delete: d node_edit_labels: l node_availability: a node_prune_images: P secret_delete: d secret_new: n forward_stop: d forward_copy_url: o

Le chargement n'échoue jamais : une touche invalide ou réservée, une action inconnue, ou deux actions associées à la même touche sur un même onglet reviennent chacune à leur valeur par défaut, et l'UI affiche les avertissements une seule fois, au démarrage.

quit et copy s'appliquent aussi dans chaque boîte de dialogue — la surcouche d'inspection, les vues de détail, le visualiseur de logs —, si bien qu'une touche réaffectée y ferme et y copie également. Pour la même raison, elles ne peuvent pas prendre une touche déjà utilisée par une boîte de dialogue, comme t, d ou i : une telle réaffectation est ignorée au profit de la valeur par défaut, avec un avertissement. L'éditeur d'env fait exception : chaque lettre y est une commande vim ou du texte, on le quitte donc avec Esc / :q et on copie avec yy, quelles que soient les touches associées à quit et copy.
