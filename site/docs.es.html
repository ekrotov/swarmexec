swarmexec_ docs

Uso del cliente — comandos, flags, configuración y la TUI.

swarmexec te ofrece docker exec -it, logs, reenvío de puertos y gestión de volúmenes contra cualquier contenedor de un Docker Swarm, desde una sola terminal. Un pequeño agente en cada nodo (un servicio global de Swarm) hace el trabajo en su nodo; el cliente pregunta al manager de Swarm en qué nodo se ejecuta tu destino y luego se conecta directamente al agente de ese nodo por mTLS. Esta página documenta el cliente.

1. Cómo funciona

Dos binarios, un único protocolo:

  • agent — se ejecuta como un servicio global de Swarm (una tarea por nodo), monta el socket de Docker de ese nodo y expone una API gRPC mínima que hace de proxy de exec / logs / reenvío de puertos hacia los contenedores de su propio nodo. Lo despliegas una vez con swarmexec init.
  • client (esta CLI) — se ejecuta en tu estación de trabajo. Habla con la API del manager de Swarm para averiguar en qué nodo se ejecuta tu destino y el id del contenedor, y luego se conecta directamente al agente de ese nodo en el puerto 9443. Los agentes no se comunican entre sí.
terminal del operador ──gRPC/mTLS──> agent(nodoN) ──docker.sock──> contenedor │ └── API del manager de Docker (resuelve nodo + id de contenedor)

La conexión con el manager usa tu contexto de la CLI de Docker (así que respeta --context, los bastiones ssh://, mTLS, etc.). La conexión con el agente se autentica mediante TLS mutuo, o con un secreto compartido contra un agente autofirmado — consulta Autenticación.

2. Instalación

Requiere Docker Engine 19.03 o posterior (API 1.40) en el manager y en cada nodo. swarmexec rechaza un daemon más antiguo en el momento de conectar, con un mensaje que indica ambas versiones, en lugar de conectarse y luego ir fallando vista a vista. Dos funciones exigen algo más al daemon del nodo: el uso de recursos en vivo y la vista de imágenes por nodo necesitan Docker 23.0 (API 1.41/1.42); con versiones anteriores quedan vacías y lo indican, en lugar de fallar.

Lo más rápido: el script de instalación elige el binario adecuado para tu máquina, lo verifica con el SHA256SUMS de la versión y se niega a instalar nada que no haya podido verificar. Nunca usa sudo ni modifica tu perfil de shell — léelo antes, es corto.

$ curl -fsSL https://swarm-exec.cloud-surfers.net/install.sh | sh $ curl -fsSL https://swarm-exec.cloud-surfers.net/install.sh | SWARMEXEC_VERSION=v1.19.2 sh # una versión concreta

Con un gestor de paquetes — así brew upgrade o scoop update traen cada nueva versión, lo que mantiene el cliente al día con los agentes:

$ brew install ekrotov/swarmexec/swarmexec # macOS, Linux $ scoop bucket add swarmexec https://github.com/ekrotov/scoop-swarmexec $ scoop install swarmexec # Windows

O a mano:

El cliente es un único binario estático. Descarga la compilación de la última versión para tu plataforma:

$ curl -fsSLo swarmexec \ https://gitlab.logle.io/cs-public/swarm-remote-exec/-/releases/permalink/latest/downloads/bin/swarmexec-linux-amd64 $ chmod +x swarmexec && sudo mv swarmexec /usr/local/bin/ $ swarmexec --version

Compilaciones: linux-amd64, linux-arm64, darwin-arm64, darwin-amd64, windows-amd64. La imagen del agente es pública en Docker Hub como logleio/swarmexec-agent.

Autocompletado de la shell

swarmexec completion bash|zsh|fish|powershell imprime un script de autocompletado. Completa algo más que flags: exec <TAB> ofrece los servicios existentes, logs web.<TAB> sus slots en ejecución, --stack <TAB> los stacks desplegados y --context <TAB> tus contextos de Docker. Solo se consulta la API del manager, nunca un agente; un autocompletado se rinde a los dos segundos y por ssh:// nunca puede pedir datos al usuario, así que un contexto que pediría una contraseña no ofrece nada en lugar de bloquear la shell.

$ swarmexec completion bash > /etc/bash_completion.d/swarmexec # o ~/.local/share/bash-completion/completions/ $ swarmexec completion zsh > "${fpath[1]}/_swarmexec" $ swarmexec completion fish > ~/.config/fish/completions/swarmexec.fish

3. Inicio rápido

Apunta tu contexto de Docker a un manager de Swarm y luego aprovisiona los agentes una sola vez. init crea un secreto compartido, despliega el agente en cada nodo en modo autofirmado y escribe la configuración de cliente correspondiente, de modo que los demás comandos funcionan de inmediato.

$ swarmexec --context my-swarm init # despliega agentes en cada nodo (una vez) $ swarmexec ps # lista las tareas y el nodo en que se ejecuta cada una $ swarmexec exec web -- sh # abre una shell en el servicio "web", esté en el nodo que esté $ swarmexec logs -f web # sigue los logs de un servicio $ swarmexec port-forward db 5432 # localhost:5432 → contenedor:5432 $ swarmexec ui # TUI interactiva

Para retirar los agentes, usa swarmexec down (deja intacta tu configuración de cliente).

4. Selectores de destino

exec, logs y port-forward reciben un destino como primer argumento. Se resuelve en este orden:

FormaEjemploSignificado
servicewebLa tarea en ejecución del servicio. Si tiene más de una réplica, es ambiguo — ver más abajo.
service.slotweb.2Un slot de réplica concreto. Durante una actualización progresiva gana la tarea más nueva del slot.
task-idxxh8k1…Un ID de tarea de Swarm.
container-id3f9a2b…Un prefijo de ID de contenedor. Necesita un nodo: pasa --node, o se localiza recorriendo las tareas en ejecución.

Ambigüedad. Un nombre de servicio a secas, con varias réplicas, no puede resolverse a una única tarea. En modo interactivo, exec te pide que elijas en una lista numerada; logs y port-forward nunca preguntan: imprimen la lista de candidatos y terminan. Deshaz la ambigüedad con un slot (web.0, web.1, …).

--node solo se tiene en cuenta para destinos de tipo container-id y puede ser un hostname, una IP o un ID de nodo. Los destinos de tipo servicio / slot / tarea se localizan a través de la API del manager, así que nunca lo necesitan.

5. Configuración

La configuración se compone de cuatro capas; cada una prevalece sobre la anterior:

valores por defecto integrados → archivo de configuración → entorno → flags de línea de comandos

Un flag solo prevalece cuando realmente lo pasas, así que un valor del archivo o del entorno se mantiene salvo que lo sobrescribas explícitamente.

Archivo de configuración

La ruta por defecto es la primera de estas que esté definida:

  1. $SWARMEXEC_CONFIG
  2. $XDG_CONFIG_HOME/swarmexec/config.yaml
  3. ~/.config/swarmexec/config.yaml

Cámbiala con --config <path>. El archivo es YAML; si no existe no pasa nada, pero uno mal formado es un error. Se escribe con permisos 0600 (puede contener el secreto compartido). El archivo de log está junto a él por defecto — ~/.config/swarmexec/swarmexec.log — salvo que definas --log-file. Claves:

Para ver la configuración efectiva resultante (con el secreto enmascarado):

$ swarmexec config show # o: --json

Usa ip cuando los hostnames de los nodos no se puedan resolver desde tu estación de trabajo — init escribe addr_mode: ip en la configuración generada precisamente por ese motivo. 6. Autenticación

El cliente se autentica ante el agente en uno de dos modos.

Modo A — TLS mutuo (por defecto)

Define ca, cert y key (los tres son obligatorios). El cliente verifica al agente con tu CA y presenta su propio certificado; el agente te autoriza y registra tu actividad en la auditoría según el CN del certificado. Es el modo por defecto y el recomendado.

$ swarmexec --ca ca.crt --cert me.crt --key me.key ps

Modo B — agente autofirmado + secreto compartido

Más sencillo de mantener (un solo secreto, sin PKI) — es lo que configura init. Define agent_secret (o agent_secret_file) y, además, una ca para verificar al agente o insecure: true para omitir la verificación. Un certificado de cliente es opcional (pero cert y key deben definirse juntos o ambos estar vacíos). Tu identidad de auditoría es el valor de operator (por defecto: tu usuario del SO).

$ swarmexec --agent-secret "$SECRET" --insecure ps
insecure omite la comprobación del certificado de servidor del agente. Esto no pone en riesgo el secreto: el cliente nunca lo envía, solo una prueba calculada a partir del secreto y del certificado de la conexión por la que viaja, así que un servidor que no has verificado no recibe nada que le sirva frente a un agente real. Lo que sí ocurre es que el agente no queda autenticado ante ti: quien responda puede leer lo que esa sesión le envíe. En cualquier red en la que no confíes, usa mejor una ca, y mantén el secreto fuera del historial de tu shell (usa agent_secret_file o el archivo de configuración).

Actualizar a v1.17.3 — primero los agentes

Un cliente v1.17.3 no puede autenticarse ante un agente más antiguo. Solo envía la prueba ligada a la conexión, y los agentes anteriores a v1.17.3 no reconocen ese formato: responden invalid or missing agent secret aunque tu secreto sea correcto. Actualízalos primero:
$ swarmexec init --force
Mientras convivan versiones distintas, legacy_secret: true en la configuración del cliente envía también el secreto en bruto, con la exposición descrita arriba. Quítalo en cuanto los agentes estén al día y vuelve a ejecutar swarmexec init --force --allow-legacy-secret=false para que ningún cliente pueda enviar la credencial por la red por accidente.

7. Contexto de Docker y SSH

--context selecciona el contexto de la CLI de Docker que se usa para la API del manager. Orden de resolución: --context → $DOCKER_CONTEXT → $DOCKER_HOST → el contexto activo en ~/.docker/config.json → el socket local unix:///var/run/docker.sock.

No se requiere Docker local. El cliente nunca ejecuta el binario docker: incorpora el SDK de Docker para Go y habla directamente con la API del manager, leyendo él mismo los metadatos de contexto de los archivos. Solo necesita un endpoint de manager de Swarm accesible (las llamadas que resuelven nodos solo funcionan contra un manager):
  • $DOCKER_HOST apuntando a un manager remoto por tcp:// (mTLS) — en ese caso no necesitas Docker instalado en tu estación de trabajo en absoluto;
  • un contexto ssh:// — necesita el cliente ssh (no docker); tanto el tráfico hacia el manager como el de los agentes viaja por ese túnel;
  • el socket local unix:///var/run/docker.sock — solo es la opción de último recurso, y la única que implica un daemon local.
La propia CLI de docker solo es necesaria para crear contextos con nombre (docker context create) — o créalos con swarmexec context create <name> --docker-host …, y así ni siquiera para eso hace falta la CLI de docker; con $DOCKER_HOST puedes prescindir por completo de los contextos con nombre. (init lee las credenciales locales de docker login solo para una imagen de agente privada — no para la pública por defecto.)

Bastión SSH. Si el host del contexto es un endpoint ssh://, la API del manager viaja por un túnel SSH — y la conexión con el agente también: como los endpoints node:9443 de los nodos normalmente no son enrutables desde tu estación de trabajo, el cliente envía automáticamente el tráfico gRPC del agente por un túnel a través del mismo host SSH. No hace falta ningún flag adicional.

$ docker context create swarm --docker host=ssh://ops@manager.example.com $ swarmexec --context swarm exec web -- sh

Basta con ejecutarlo una vez por swarm.

wait — esperar a que un despliegue haya convergido de verdad

stack deploy termina cuando swarm ha aceptado el cambio, no cuando este funciona. wait cubre ese hueco en un pipeline: se bloquea hasta que todos los servicios indicados — o todos los de --stack — han convergido y entonces sale con 0; si alguno no lo consigue, sale con 1 y el motivo.

swarmexec stack deploy shop.yml --yes && swarmexec wait --stack shop --timeout 3m swarmexec wait api worker --healthy

Convergido significa que no hay ninguna actualización en curso y que hay tantas tareas en ejecución como las deseadas (en un job: que se ha alcanzado el número de finalizaciones), y que eso se mantiene en dos consultas separadas por unos segundos. Por eso incluso un servicio estable tarda unos segundos, y el instante justo después de un despliegue, antes de que el manager haya iniciado la actualización, no puede pasar por terminado. Dos estados que parecen estables cuentan como fallos: una actualización pausada (el servicio ejecuta una mezcla de tareas antiguas y nuevas) y un rollback completado durante la espera (ejecuta la spec anterior: el despliegue no se aplicó). Si se agota el tiempo, se imprime el motivo por el que una tarea no se ejecuta, normalmente el propio mensaje del planificador. Con --healthy, además, todo contenedor con healthcheck debe estar sano; un nodo cuyo agente no puede informar del estado de salud cuenta como todavía no, nunca como sano. swarmexec solo observa e informa: nunca hace rollback ni reintenta.

Comprueba la conexión con el manager y si el servicio del agente está desplegado, y sondea el agente de cada nodo en estado ready para verificar que es accesible y que su versión coincide. security report — un informe Markdown de todo el clúster

El overlay de riesgos de seguridad analiza las specs de los servicios y muestra el resultado en pantalla. Este comando escribe ese mismo análisis — más las comprobaciones que corresponden al clúster y no a un servicio concreto — en Markdown, para revisarlo lejos de la terminal, adjuntarlo a un ticket, o versionarlo junto a tus archivos de stack y compararlo de una versión a otra. Se escribe en stdout salvo que se indique -o, así que se puede pasar por una tubería con la misma facilidad con que se guarda.

swarmexec security report -o security.md

Cuatro comprobaciones se ejecutan a nivel de clúster; ninguna de ellas se puede responder a partir de la spec de un servicio:

ComprobaciónSeveridadQué señala
network-unencrypted — «el tráfico overlay no está cifrado»mediumuna red overlay que transporta tráfico de servicios sin cifrado del plano de datos. Swarm envía el tráfico de los contenedores entre nodos por túneles VXLAN en claro, a menos que la red se haya creado con --opt encrypted, y el servicio en ejecución se ve exactamente igual en ambos casos. Las redes sin nada conectado no se señalan — no transportan nada —, y tampoco ingress, que no se puede cifrar, de modo que un hallazgo sobre ella nunca podría resolverse
autolock-disabled — «los managers no tienen autolock»mediumel almacén raft de los managers no está cifrado en reposo. Contiene todos los secretos, todos los configs y la clave de la CA del clúster, y su clave de cifrado está en el mismo disco: quien se lleve el disco de un manager se lo lleva todo. Actívalo con docker swarm update --autolock=true y guarda la clave de desbloqueo: un manager reiniciado la pedirá. Si no se puede leer la configuración del swarm, el informe dice autolock-unknown en lugar de suponer nada: dar por hecho «desactivado» inventaría un hallazgo, y dar por hecho «activado» daría una falsa sensación de seguridad
agent-proto-mismatch / agent-version-skew / agent-too-old / agent-unreachablehigh / medium / lowel agente es quien aplica la autorización en cada exec, cada log y cada port-forward, así que uno más antiguo que tu cliente puede no aplicar una regla que el cliente da por hecha. Una discrepancia de protocolo es high y pesa más que una diferencia de versión: los dos extremos no coinciden en el propio contrato, no solo en qué compilación lo implementa. Un agente que no respondió se informa como laguna, no como superado. El desfase de versiones no se informa para un cliente no publicado (dev), que por definición difiere de todo agente publicado — la misma excepción que aplica doctor
unused-secret / unused-configlowun secreto o config al que no hace referencia ningún servicio. Se sigue distribuyendo a través del almacén raft y sigue siendo legible para cualquier cosa que llegue a un manager — normalmente es una credencial que alguien rotó y nunca eliminó, con lo que el valor antiguo sigue vigente en el clúster mucho después de que todos lo den por desaparecido

Lo que el informe dice de sí mismo. Lo lee, lejos de la terminal, alguien que no estaba presente cuando se ejecutó, así que incluye su propio contexto: qué clúster, cuándo y con qué compilación. También tiene una sección Not covered — agentes inalcanzables, configuración del swarm ilegible, lista de nodos vacía — porque en un informe de seguridad el silencio se interpreta como «todo en orden» incluso sobre terreno que nunca se examinó. El orden depende únicamente de los hallazgos, así que dos informes de un clúster sin cambios solo difieren en la marca de tiempo y se pueden comparar entre sí; y eso solo tiene valor porque la ausencia de un hallazgo significa no encontrado y nunca no revisado.

El archivo se escribe con permisos 0600, y los directorios padre que falten se crean con 0700. Nombra cada servicio, cada red y cada secreto del clúster junto con cada debilidad encontrada: es un mapa de por dónde atacar, y no tiene por qué poder leerlo cualquier cuenta de la máquina.

Se recopilan de nuevo los datos de todo el clúster —no es un volcado de lo que muestra el overlay— y se hace fuera de la goroutine de la interfaz, de modo que esta sigue respondiendo mientras se consulta cada nodo.

stack export / stack diff — un stack desplegado como archivo

stack export lee del clúster un stack desplegado y lo escribe como YAML con formato compose. stack diff compara un archivo de stack con lo que está realmente desplegado e imprime un diff unificado: una línea + es algo que desplegar el archivo añadiría; una -, algo que quitaría. Igual que git diff --exit-code, termina con 1 si hay cualquier diferencia, así que sirve en CI.

swarmexec stack ls swarmexec stack export postgres -o postgres.yml swarmexec stack diff postgres.yml postgres

En la TUI, E en la pestaña Stacks/Services ofrece ambas cosas para el stack bajo el cursor: la fila del stack, uno de sus servicios o un contenedor de alguno de ellos.

Por qué no compara texto. Un stack desplegado contiene cosas que el archivo nunca tuvo: el digest de la imagen que el daemon resolvió al desplegar, sus propios valores por defecto de las políticas de reinicio y de actualización, y el espacio de nombres del stack antepuesto a cada red, secreto y volumen. Comparar ambos como texto daría decenas de diferencias para un stack perfectamente sincronizado — y eso es peor que no tener herramienta, porque te acostumbra a ignorar la salida. En su lugar, el archivo pasa por el propio cargador y conversor de compose de docker, el mismo código que usa docker stack deploy, y después ambos lados se normalizan con la misma función. La pregunta que se responde es «¿cambiaría algo desplegar este archivo?», no «¿están escritos igual estos dos archivos?». Los valores por defecto del daemon se descartan en ambos lados; un valor que no es el predeterminado sigue apareciendo, así que no se oculta nada real.

Una exportación es una descripción, no una copia de seguridad. El valor de un secreto es de solo escritura en la API del engine —nunca puede volver a leerse— y el contenido de un volumen reside en los nodos. Por eso ambos se declaran external, y el archivo exportado lo indica en su propia cabecera: recrear el stack en otro lugar implica crear antes los secretos. Los campos de la spec que esta representación no incluye (tty, ulimits, los ajustes de seccomp y AppArmor y algunos más) se enumeran en el mismo lugar, porque el fallo peligroso de una herramienta de comparación no es una respuesta equivocada, sino un silencio que aparenta seguridad: por eso «sin diferencias» llega siempre acompañado de sus salvedades.

Las variables se interpolan desde tu entorno, exactamente como hace docker stack deploy. Un archivo que contiene ${TAG} describe, por tanto, un stack distinto para cada TAG, y el diff depende del entorno en el que se ejecuta — y es lo correcto: hacer como si no fuera así informaría «sin cambios» para un despliegue que cambiaría la imagen.

ComandoDescripción
stack lslos stacks desplegados en el clúster
stack export <stack>escribe el stack como YAML de compose; con -o, en un archivo; si no, en stdout
stack diff <file> [stack]compara un archivo con el stack desplegado. Por defecto, el nombre del stack es el del archivo sin extensión; --stack o un segundo argumento lo sustituyen. Termina con 1 ante cualquier diferencia

Como control en un pipeline. Ejecutado cada noche, stack diff responde a «¿sigue el clúster igual que en Git?»: el código de salida 0 significa que no hay diferencias; 1, que hay alguna; 2, un error de uso; 125, que el manager es inalcanzable. Un control que se pone en rojo con cada cambio inofensivo acaba desactivado, por eso --ignore excluye un campo de ambos lados — services.*.deploy.replicas para un número de réplicas que cambia un autoescalador, con * para cualquier nombre de servicio; repítelo para varias rutas. Cada ruta ignorada aparece en Not compared, para que un resultado en verde siga diciendo lo que no revisó, y una ruta que no coincide con nada en ninguno de los dos lados se señala, porque, si no, una errata en la lista de exclusiones no excluiría nada, sin avisar. --format json imprime el formato legible por máquinas: differs, los hunks, ignored y not_compared.

swarmexec stack diff shop.yml --ignore 'services.*.deploy.replicas' swarmexec stack diff shop.yml --format json | jq .differs

stack deploy — aplicar un archivo de stack, tras comprobarlo

Carga un archivo de stack, ejecuta las comprobaciones de seguridad sobre lo que realmente desplegaría y lo aplica. Lo que aporta frente a docker stack deploy es el control previo: el archivo se comprueba antes de crear nada y, si aparece algo por encima del nivel informativo, el despliegue se detiene y pregunta.

swarmexec stack deploy web.yml # pregunta si encuentra algo swarmexec stack deploy web.yml --check # solo comprobar, nunca desplegar swarmexec stack deploy web.yml --force # desplegar pese a los hallazgos, a conciencia

En la TUI, E → deploy a file hace lo mismo: primero se muestran los hallazgos; d continúa y Esc cancela. En ese punto todavía no se ha creado nada, que es precisamente para lo que sirve la pausa.

Las comprobaciones no son un segundo conjunto de reglas. El archivo se convierte exactamente en los valores ServiceSpec que enviaría el despliegue, y sobre ellos se ejecutan los ocho analizadores existentes — las mismas comprobaciones que ponen el escudo en el árbol y alimentan el overlay ! y el informe de seguridad. Dos conjuntos acabarían divergiendo: una regla endurecida en un sitio y no en el otro haría que el control dejara pasar un archivo que el árbol marca en cuanto está en ejecución, y al operador al que se le dijo «nada encontrado» se le habría dicho algo falso. Además, así las comprobaciones ven lo que el clúster hará, no lo que el archivo dice: entre ambos están los valores por defecto y las abreviaturas de compose.

--yes no significa «ignora los hallazgos». Significa «no preguntes», y una ejecución que encuentra algo por encima del nivel informativo se niega igualmente a desplegar y termina con un código distinto de cero. De lo contrario, el control se convertiría en un mero trámite la primera vez que alguien lo pusiera en CI. Para desplegar pese a los hallazgos hay que indicar --force, que es algo distinto que teclear y algo distinto que explicar después. Una ejecución no interactiva sin respuesta en stdin cuenta como no.

FlagDescripción
--checkejecuta las comprobaciones y se detiene. Termina con 1 si encontró algo por encima del nivel informativo, así que sirve de control en un pipeline
-y, --yesno pregunta. Despliega si las comprobaciones no encuentran nada; si no, se niega
--forcedespliega pese a los hallazgos, sin preguntar
--pruneelimina los servicios del stack que el archivo ya no declara. Desactivado por defecto, como en docker: un archivo que solo contiene parte del stack es, con mucha más frecuencia, un descuido que una instrucción de borrar

Qué hace un despliegue, en este orden: redes, luego secretos, luego configs y por último servicios — un servicio que hace referencia a algo que aún no existe falla, y el stack queda aplicado a medias. Las redes externas se comprueban primero, porque una que no existe es el motivo más habitual de que un despliegue se quede a medias. Un secreto existente nunca se sobrescribe: su valor es inmutable en swarm, así que cambiarlo implica crear uno nuevo con otro nombre. Si aun así un despliegue falla a mitad, lo que ya se había aplicado se indica junto al error en lugar de dejar que lo adivines.

Política de autorización

Por defecto, un agente permite toda petición que haya superado la autenticación. Un archivo de reglas lo restringe: qué acciones (container.list, container.events, exec, logs, portforward, stats.read, image.list, image.prune, image.prune.all, volume.list, volume.create, volume.remove; se admiten patrones como volume.*) para qué servicios, puertos, usuarios de exec y — solo con certificados de cliente — identidades de operador. Dentro de una regla deben cumplirse todas las condiciones; decide la primera regla que coincide, y default (obligatorio) cubre el resto.

# policy.yaml — decide la primera regla que coincide; "default" si no coincide ninguna default: allow rules: - deny: [image.prune.all] reason: no sweeping prune on production - deny: [portforward] ports: [5432, 3306] reason: no forwards to the databases - deny: [exec] users: [root, "0", "0:0"] - deny: ["volume.*"] services: ["prod_*"]
swarmexec init --force --policy-file policy.yaml

Un rechazo llega al cliente como permission denied con la regla y su motivo, y el mismo texto queda en el log de auditoría. init valida el archivo antes de desplegar nada, y el agente se niega a arrancar con uno que no puede leer: una acción desconocida, una clave mal escrita o un patrón incorrecto son un error, nunca una regla que en silencio no coincide con nada. Las reglas sobre identities se rechazan mientras los agentes usen un secreto compartido sin certificados de cliente, porque en ese caso la identidad es la que el cliente diga. Un exec sin -u se ejecuta con el usuario de la imagen, que el agente no ve; users: [""] lo cubre. Cambia el archivo y vuelve a ejecutar init --force; si lo ejecutas sin el flag, la política se elimina.

Lo que no es. Una política evita accidentes y deja constancia de la intención — nada de prune total en producción, nada de reenvíos a la base de datos. No es control de acceso: todo lo que swarmexec cambia en servicios, secretos, redes y stacks va al manager del swarm con tus propias credenciales de Docker y nunca pasa por un agente, y quien tenga esas credenciales puede desplegar un servicio que sea root en todos los nodos. Para eso, restringe las credenciales de Docker.

Volver a desplegar los agentes sin cambiar el secreto

Tarde o temprano tendrás que volver a desplegar los agentes en un swarm ya aprovisionado: un agente se queda colgado, doctor muestra un nodo como too old (init --force), un comando falla con «agent is older than this client (missing RPC) — update it with swarmexec init --force», o un nodo se ha reconstruido y su agente no volvió a levantarse. La solución es volver a ejecutar init con --force, que le indica que actualice el servicio si ya existe. Sin ese flag, ejecutar init sobre un servicio existente es un error de uso que te pide añadir --force; no se cambia nada.

$ swarmexec init --force

Esto vuelve a desplegar el agente en cada nodo y deja intacto el secreto compartido. Los secretos de Docker son inmutables, así que init encuentra el swarmexec_agent_secret existente, lo indica como reusing existing y conserva el valor que ya está en el clúster. Todo cliente que funcionaba antes del redespliegue sigue funcionando: no hay que redistribuir nada.

No pases --secret al volver a desplegar. Si el secreto ya existe no se puede sobrescribir, así que tu valor no se aplica al clúster, pero sí se escribe en tu configuración de cliente. Salvo que coincida por casualidad con el valor real del secreto existente, los agentes te rechazarán a partir de ese momento, y el fallo aparece más tarde con la apariencia de un agente averiado y no de una configuración local equivocada. init avisa exactamente de esto cuando ocurre; tómate el aviso en serio. Para cambiar de verdad el secreto del clúster, tienes que eliminar primero el secreto (ningún servicio puede hacer referencia a él) y volver a ejecutar init.

--save-config vale true por defecto, así que un redespliegue también reescribe ~/.config/swarmexec/config.yaml. Pasa --save-config=false siempre que la configuración local del cliente deba quedar intacta: por ejemplo, cuando vuelves a desplegar los agentes desde una máquina cuya configuración ya es correcta, o desde CI.

$ swarmexec init --force --save-config=false

Después, comprueba el resultado. doctor informa de un estado por nodo; ok en todos ellos significa que cliente, agente y secreto vuelven a coincidir.

$ swarmexec doctor

Análisis y filtrado según el formato. --log-format le indica al cliente cómo leer cada línea para poder extraer un nivel y un mensaje: classic extrae el nivel de una línea de texto plano —un campo entre corchetes ([error], [ info]), una palabra en MAYÚSCULAS o una seguida de dos puntos (error:), que es lo que evita que un nodo llamado node-error-2 pinte de rojo cada línea que lo menciona—; json analiza JSON al estilo de logstash (campos level/message); logfmt analiza el estilo key=value que usan muchas aplicaciones Go, el daemon de Docker y las herramientas de HashiCorp (msg/message, level/lvl/severity, ts/time), gelf analiza el JSON GELF de Graylog (nivel de syslog numérico); y raw deja las líneas sin cambios. --min-level descarta entonces todo lo que esté por debajo del nivel elegido, y --grep conserva solo las líneas cuyo mensaje analizado coincide con la expresión regular.

Las líneas sin nivel detectable siempre pasan el filtro --min-level, de modo que no se pierden los stack traces multilínea. Los mismos valores por defecto se pueden fijar una sola vez en la sección logs: de la configuración (los flags tienen prioridad).

Seguimiento aunque se reemplace el contenedor. Con -f sobre un destino de tipo service o service.slot, logs sigue mostrando los logs cuando el contenedor del que lee se reemplaza por una actualización progresiva, un reinicio o una reprogramación: vuelve a resolver el contenedor del servicio que está en ejecución en ese momento (el mismo slot, o el mismo nodo en un servicio global), se reconecta automáticamente —como docker service logs -f— e imprime una línea de aviso atenuada (container replaced; reconnected to <id> on <node>). Espera hasta ~30 s a que se programe un reemplazo antes de rendirse, y termina limpiamente si se elimina el servicio. Un destino de tipo container-id a secas no tiene sucesor, así que simplemente se detiene, como antes.

La detección se hace en el cliente: obtiene la topología del manager de swarm al que ya está conectado — cada agente solo conoce su propio nodo y no puede ver los reemplazos a nivel de swarm.

Varias fuentes a la vez. Con varios destinos, un servicio con varias réplicas o --stack <name>, logs sigue todas las fuentes juntas: un servicio equivale a todas sus réplicas en ejecución, como con docker service logs. Cada línea lleva como prefijo su origen — web.2, o agent@node-3 para un servicio global—, con relleno para que los mensajes queden alineados, y en color en una terminal (nunca con NO_COLOR definido ni al redirigir a una tubería). Cada fuente se reconecta por su cuenta cuando se reemplaza su contenedor y detecta su propio formato con --log-format auto, porque cada servicio escribe sus logs de forma distinta; las líneas se intercalan enteras, nunca mezcladas entre fuentes. Una fuente que falla lo indica en sus propias líneas y no detiene a las demás; el código de salida lo refleja al final. Un único destino que es un solo contenedor se muestra exactamente como antes, sin prefijo.

Las líneas se intercalan en el orden de llegada, no ordenadas por tiempo entre fuentes — añade -t cuando importe el orden entre servicios. Cada fuente es un stream abierto contra el agente de su nodo y cuenta para el límite -max-streams de ese agente.
$ swarmexec logs -f --tail 100 web $ swarmexec logs --since 15m -t web $ swarmexec logs --log-format json --min-level warn web $ swarmexec logs --log-format auto --min-level warn web # que decidan las líneas $ swarmexec logs --grep 'timeout|refused' -f web $ swarmexec logs -f api worker db $ swarmexec logs -f --tail 20 --stack shop
Detectar el formato. --log-format auto —y a en la vista de logs de la TUI— evalúa las propias líneas con cada formato integrado y elige el primero, del más específico al menos, que explique al menos dos de cada tres líneas. GELF se comprueba antes que JSON porque toda línea GELF también es JSON válido; una línea key=value solo cuenta como logfmt si lleva una clave msg o level, de modo que ni la query string de una URL ni un access log cuentan. Se toman como muestra las líneas más recientes, no las primeras, que suelen ser el banner de arranque de un framework y no la aplicación. Si la muestra es demasiado pequeña o demasiado heterogénea, lo indica y se queda con el valor por defecto en lugar de adivinar: un formato equivocado es peor que ninguno, porque --min-level sobre un flujo mal analizado no filtra nada. Cuando la salida va a una tubería, las primeras líneas se retienen hasta tener un veredicto (como mucho 40 líneas, como mucho un segundo), para que la salida nunca se imprima en dos formatos. Pendiente para más adelante: la detección por servicio a partir de un catálogo en línea indexado por imagen — el mismo punto de extensión, con otra fuente para la respuesta.

Conexiones ssh compartidas

Con un contexto ssh://, swarmexec llega al clúster por ssh por partida doble: a la API del manager de Docker, a través del helper de conexión de ssh, y a cada agente de nodo, por su propio túnel hacia el mismo host. Hasta ahora, cada exec, cada flujo de logs, cada reenvío de puertos, cada consulta de estadísticas y cada ciclo de refresco abría una conexión ssh nueva — un handshake TCP, un intercambio de claves y una autenticación por conexión, y otro tanto por cada host de salto — contra un bastión al que se había conectado un instante antes.

Ahora swarmexec hace que compartan un único transporte, usando el propio ControlMaster de OpenSSH: la primera conexión a un destino lo abre y cada una de las siguientes pasa a ser un canal sobre él. Medido en un clúster de tres nodos detrás de un host de salto, swarmexec doctor pasó de 8 autenticaciones y 3,6 s a 2 y 1,0 s. El tráfico en sí no cambia, y el efecto es mayor cuanto más hagas en una sesión.

  • Los sockets de control viven en $XDG_RUNTIME_DIR/swarmexec/ssh/ (o, en su defecto, en tu directorio de caché), creado con 0700 — un socket de control es una sesión autenticada activa, así que se queda dentro de tus propios directorios y nunca en /tmp.
  • Un socket por destino y ruta: dos contextos que alcanzan el mismo manager por hosts de salto distintos no comparten nada, porque no son la misma conexión.
  • La conexión compartida sigue abierta 60 s después de que termine el comando, para que el siguiente sea rápido, y luego se cierra sola. Después, swarmexec no deja ninguna conexión abierta.
  • Un socket que haya dejado un proceso maestro terminado a la fuerza es inofensivo: ssh detecta que está muerto y abre una conexión normal en su lugar.
  • No está disponible en Windows, cuyo OpenSSH no implementa conexiones compartidas. En el resto de sistemas, SWARMEXEC_SSH_MULTIPLEX=0 lo desactiva — conviene saberlo si configuras ControlPath por tu cuenta, ya que el ajuste de swarmexec se pasa en la línea de comandos de ssh y, por tanto, tiene prioridad sobre ~/.ssh/config.

Comprobación de versión de :latest. Swarm fija :latest a un digest en el momento del despliegue, así que un servicio con el tag :latest en realidad ejecuta una imagen fija. swarmexec lo consulta en el registro (con tus credenciales locales de docker) y anota la fila del servicio justo después de la URI de la imagen: la versión real entre paréntesis —leída de la etiqueta org.opencontainers.image.version de la imagen— y una flecha hacia arriba ↑ cuando el :latest actual del registro es un digest más nuevo que el que tiene fijado el servicio (p. ej. nginx:latest (1.4.0) ↑). Funciona en la medida de lo posible y se guarda en caché: si el registro da error, la fila simplemente queda sin anotar. La sección IMAGE del overlay de inspección muestra la misma versión y, cuando existe una imagen más nueva, una fila seleccionable newer version available: sitúate sobre ella y pulsa u (o Enter) para actualizar el servicio.

Fijar una versión con u: no solo cuando hay una actualización. u no depende de que se ofrezca una actualización. Está disponible en cualquier inspección de servicio cuyos tags de imagen haya podido leer swarmexec del registro —tanto en servicios fijados a una versión como en los que usan :latest— y desde cualquier fila del overlay, así que nunca tienes que buscar la indicación. Volver a aplicar la misma versión, fijar la que está en ejecución o volver a un tag más antiguo son usos totalmente normales; no hace falta esperar a que haya una actualización. El texto del pie te indica en qué situación estás: u update version cuando se encontró una versión más nueva (entonces también aparece la fila newer version available, con un destino concreto) y u set version cuando no.

Lo que abre u depende de lo que sepa el registro. En un servicio fijado a una versión para el que hay una versión más nueva, abre el selector de versión: un campo cuyo autocompletado sugiere los tags más nuevos de la misma familia, del más alto al más bajo y con el más alto ya rellenado. En uno que ya está en el tag más nuevo, es el mismo selector, pero las sugerencias pasan a ser todos los tags que lista el repositorio (con el tag en ejecución ya rellenado): así es como fijas una versión o vuelves a una anterior. Un servicio en :latest también recibe el selector, con todos los tags conocidos: elegir ahí una versión concreta es la forma de sacar un servicio :latest del tag flotante y fijarlo, que es justo lo que pide el hallazgo de riesgo unpinned-image (ver el overlay de riesgos de seguridad más abajo). La única excepción es un servicio :latest con una actualización de digest pendiente: ahí se mantiene la confirmación única del nuevo digest del registro de siempre, porque un selector invitaría a escribir latest, que resuelve al tag sin digest y descartaría sin avisar precisamente la fijación por digest que la actualización pretende renovar.

En el selector, la lista de sugerencias está limitada a 25 entradas (un repositorio muy activo puede listar cientos) y el campo sigue siendo de texto libre, así que puedes escribir cualquier tag existente, incluido uno más antiguo para fijarlo o volver a una versión que sabes que funciona. Un tag escrito a mano se valida contra el repositorio (si no figura en él, se rechaza), y elegir uno más antiguo muestra un aviso de downgrade antes de aplicarlo. En todos los casos el cambio es un único ServiceUpdate / actualización progresiva, previa confirmación. Si el registro no devolvió ningún tag y tampoco hay un destino concreto al que recurrir —un registro privado o inalcanzable, o un servicio fijado por digest—, recibes un aviso explicativo y no se cambia nada.

Se muestran todos los servicios (incluso los escalados a cero); cada fila se presenta como una línea de docker service ls —nombre, modo, tareas en ejecución/deseadas, imagen y puertos publicados— y se colorea según su estado real: la relación en ejecución/deseadas fija el color base (aqua = todas las tareas activas, naranja = parcial, rojo = caído, gris = escalado a cero) y un healthcheck que falla tiene prioridad sobre él (ver más abajo). Un marcador ▸/▾ indica si un servicio está contraído o expandido; sus contenedores en ejecución cuelgan debajo. Un servicio en mitad de una actualización progresiva lleva un distintivo de color en su fila del árbol — ⟳ updating o ↺ rolling back — y el mismo estado aparece en el overlay de inspección del servicio; desaparece en cuanto termina la actualización.

Un job se cuenta por lo que ha terminado, no por lo que está en ejecución. Un replicated-job o un global-job no está pensado para seguir activo, así que su fila muestra completadas/total en lugar de en ejecución/deseadas: un job que ha terminado se ve como un 3/3 en aqua donde antes se veía como un 0/1 en rojo —el aspecto de una caída, para un servicio que hizo exactamente lo que se le pidió—. Swarm informa del número deseado de un replicated job como su MaxConcurrent, y por eso el recuento en vivo deja de decir nada útil una vez que el job ha terminado. La fila del stack que lo contiene lo cuenta igual, de modo que una copia de seguridad nocturna ya no tiñe de naranja todo su stack entre ejecuciones.

Color según el healthcheck, no solo según el número de réplicas. Antes, el color de una fila de servicio dependía únicamente de las tareas en ejecución frente a las deseadas: así, un servicio con todos sus contenedores fallando el healthcheck seguía apareciendo como un tranquilo 3/3 en aqua. El recuento era cierto, pero la fila engañaba. El estado de las tareas de Swarm tampoco ayuda: una tarea figura como running aunque su contenedor falle todas las sondas, así que el veredicto tiene que venir del nodo. Ahora una sonda que falla se trata como una degradación del mismo tipo que una réplica que falta:

  • todos los contenedores comprobados en unhealthy → la fila se pone roja, que es tan malo como que no haya ninguno en ejecución;
  • algunos en unhealthy → naranja, como un despliegue a medias;
  • todos en healthy → el color que ya le daba el número de réplicas, sin tocar;
  • contenedores que no declaran healthcheck → la fila no cambia de color. No se sabe nada de ellos, y suponer algo sería el mismo error en sentido contrario.

Los marcadores. Una fila de servicio lleva ✖ N unhealthy en rojo, o ◌ N starting en amarillo mientras las sondas todavía no se han superado; una hoja de contenedor lleva ✖ unhealthy / ◌ starting. Unhealthy tiene prioridad sobre starting: es el que exige actuar. Una fila de stack acumula ese mismo marcador para todo lo que contiene (ver Agrupado por stack más abajo). Un contenedor sano no recibe ningún marcador, y tampoco uno sin healthcheck, para que el marcador siga significando algo. Conviven con los marcadores de recursos cpu/mem descritos más abajo, y el estado de salud va primero en la fila: es lo que contradice al recuento que tiene al lado.

De dónde sale el veredicto — y qué cuesta. Nada extra: viaja junto con las lecturas de recursos descritas más abajo, el mismo agente, la misma llamada, ninguna petición adicional a la API. La lista de contenedores que el agente ya obtiene en cada ronda de muestreo incluye el veredicto en su línea de estado (Up 3 days (healthy)), la misma cadena que imprime docker ps. El parser es deliberadamente estricto: lo que no reconoce se convierte en sin veredicto y no en una suposición, así que si algún día el daemon cambia el texto de esa línea, swarmexec deja de afirmar que lo sabe en lugar de dar por sano un contenedor que falla. Además, rige el mismo requisito que para las cifras de uso: hacen falta agentes de esta versión o posteriores, así que un clúster cuyos agentes no se han vuelto a desplegar no muestra ningún marcador de salud hasta que los despliegues con swarmexec init --force.

Marcadores de CPU y memoria en vivo. Junto a esos distintivos, una fila puede mostrar también lo que está usando en este momento; hasta ahora swarmexec solo podía mostrar lo que el planificador había reservado (ver la pestaña Nodes más abajo). Un contenedor —o un servicio— cuyo uso supera el 70% recibe un marcador naranja, y a partir del 90%, uno rojo, al final de la fila: el recurso indicado con palabras —cpu o mem— seguido del porcentaje (cpu 94%, mem 91%). Si ambos están al límite, aparecen los dos. Palabras en lugar de símbolos, y con el mismo ancho: un marcador cuyo significado hay que consultar no cumple su función, y unas letras se muestran bien en cualquier terminal. Por debajo del 70% no se dibuja nada, para que los marcadores sigan siendo una señal y no ruido de fondo. Una fila de servicio toma la peor de sus réplicas, no la media: una media esconde precisamente el contenedor que está a punto de caer, que es justo el que interesa ver. (La memoria absoluta de una fila de servicio es la suma de todas las réplicas; el porcentaje es el máximo.)

Porcentaje de qué. Cada uno se mide respecto a lo que ese contenedor puede usar realmente: su propio límite si lo tiene, y la capacidad del nodo si no. Ahí está la clave: el 91% de un límite de 256 MB significa que un OOM kill está cerca; el 91% de un nodo de 64 GB es otra historia. La vista de stats del overlay de inspección muestra el numerador y el denominador de esa división para cada contenedor e indica la base debajo de la tabla.

De dónde salen las cifras — y por qué tardan un poco. El uso no está en la API del manager: las estadísticas de los contenedores son locales a cada nodo. Proceden de un RPC del agente de cada nodo (Stats); cada agente muestrea sus propios contenedores en segundo plano y responde desde memoria, así que el cliente simplemente lo consulta en el ciclo de refresco que ya tenía. Esto tiene dos consecuencias. Un porcentaje de CPU es un delta entre dos lecturas, así que no existe hasta que el agente ha tomado dos (unos pocos segundos) — mientras tanto, las vistas muestran …, nunca 0%; la memoria no necesita delta y aparece desde la primera lectura. Además, un agente solo muestrea mientras alguien está mirando: se detiene alrededor de un minuto después de la última petición y descarta sus lecturas en lugar de servirlas desactualizadas. Por eso las primeras cifras tardan un momento en aparecer después de abrir la UI. Es deliberado: un agente al que nadie consulta no debe costar nada.
¿No ves ningún marcador? Revisa la versión del agente. El uso es información complementaria y, si falta, no da error: un nodo cuyo agente no es accesible —o es anterior a esta versión y, por tanto, no conoce el RPC Stats— simplemente no aporta lecturas. Los marcadores no aparecen, tampoco el bloque del nodo, y todo lo demás sigue igual; además, el cliente deja de consultar ese nodo durante un rato en lugar de sondearlo en cada refresco. Así que en un clúster cuyos agentes aún no se han vuelto a desplegar no hay ninguna cifra de uso ni ningún marcador de salud hasta que se actualicen los agentes — despliégalos con swarmexec init --force. Es, con diferencia, el motivo más probable de que no veas nada.

Agrupado por stack. docker stack deploy etiqueta cada servicio que crea con com.docker.stack.namespace. swarmexec lee esa etiqueta de la spec del servicio que el manager ya devolvió —Swarm no tiene ningún objeto «stack», y la etiqueta es el único vínculo— y organiza el árbol en tres niveles: stack → servicio → contenedor. Una fila de stack muestra el nombre del stack, cuántos servicios contiene y la suma de tareas en ejecución/deseadas ((3 svc · 7/8)), coloreada exactamente con la misma regla que una fila de servicio: según esa suma de tareas en ejecución/deseadas, con la misma prioridad del healthcheck por encima. Detrás van los contadores agregados, cuando no son cero: ⟳ n —servicios de ese stack en mitad de una actualización progresiva—, 🛡 n —servicios con un hallazgo de seguridad que merece acción, el mismo escudo que llevan las filas de servicio— y después el marcador de salud, ✖ N unhealthy o ◌ N starting, sumado sobre todos los contenedores de todos los servicios del stack. Así, incluso un stack contraído te indica si algo de su interior necesita atención. Que el estado de salud se agregue hacia arriba importa sobre todo aquí: la fila de stack es la que un operador revisa primero, así que un «todo está en marcha» engañoso es peor en ese nivel que en el de abajo, no mejor.

Los servicios creados con docker service create no llevan etiqueta de stack; se agrupan bajo (no stack), que siempre aparece en último lugar para no desplazar hacia abajo a los stacks reales. No se oculta nada: cada servicio sigue apareciendo exactamente una vez. Los stacks se ordenan por nombre y empiezan expandidos, así que el árbol agrupado muestra los mismos servicios que la lista plana; los nodos que contraigas se mantienen tras el refresco automático.

La agrupación está activada por defecto, pero solo tiene efecto cuando al menos un servicio del clúster lleva realmente una etiqueta de stack: en un clúster sin stacks, el árbol se ve exactamente igual que siempre, sin un padre (no stack) innecesario. Pulsa s para cambiar entre el árbol agrupado y la lista plana de servicios (el pie lo muestra como s stacks); si no hay ninguna etiqueta de stack, lo indica en lugar de volver a dibujar un árbol idéntico. La tecla se puede reasignar como stack_group en keys.yaml.

La búsqueda (/) no cambia: el filtro sigue aplicándose a servicio, contenedor y nodo. Un stack que queda vacío con el filtro desaparece del árbol, y los contadores de cada fila de stack describen lo que realmente ha quedado debajo, así que reflejan el filtro en lugar de anunciar servicios que has filtrado.

El menú de acciones ofrece logs, bash, sh, shell as user… (pide un usuario/UID, como docker exec -u, para imágenes cuyo usuario por defecto no tiene las herramientas o los permisos que necesitas) y port forward (las shells no disponibles aparecen atenuadas tras comprobarlo). En la barra de búsqueda, Enter conserva el filtro y vuelve a la lista; Esc borra el filtro y cierra la barra.

Riesgos de seguridad (!). Cada vez que se obtiene la lista de servicios, swarmexec ejecuta un conjunto de pequeños analizadores estáticos sobre la spec de cada servicio —la misma spec que el manager ya devolvió—, así que no hay ninguna llamada extra a la API, el agente no interviene y no se ejecuta nada dentro de tus contenedores. Un servicio con un hallazgo que requiere acción se marca con un 🛡 al principio de su fila en el árbol de servicios, en un hueco de ancho fijo delante del nombre, de modo que los escudos quedan alineados en una columna fácil de recorrer con la vista. Pulsa ! para abrir el overlay de riesgos de seguridad, y w dentro de él para escribir un informe Markdown de todo el clúster, que cubre más que el overlay: añade las comprobaciones que corresponden al clúster y no a un servicio.

no-resource-limits — «no resource limits»lowla tarea no fija ni límite de CPU ni límite de memoria, así que un contenedor descontrolado puede consumir el nodo entero y dejar sin recursos a todo lo demás. Solo informativo — ver más abajo
unpinned-image — «image not pinned»lowla imagen está fijada a :latest, o no lleva ningún tag (lo que equivale a :latest): la versión en ejecución puede cambiar sin que cambie la spec, así que el despliegue no es reproducible. Una imagen fijada por digest (…@sha256:…) es exactamente reproducible y nunca se señala, y los dos puntos que forman parte del puerto del host del registro (registry:5000/img) no se confunden con un tag. Solo informativo — ver más abajo

Por qué las comprobaciones informativas nunca marcan un servicio. Solo un hallazgo por encima de low —high o medium— hace que un servicio requiera acción y pone el 🛡 en su fila del árbol. Los de nivel low (no-resource-limits, unpinned-image y el «no user set» de root-user) se dan en casi todos los servicios de un clúster real: marcarlos pondría un escudo en casi todas las filas y destruiría precisamente la señal visual inmediata para la que existe el marcador. Aun así, no se esconden: en cuanto un servicio queda marcado por otro motivo, sus hallazgos low se listan junto al resto en el overlay, es decir, donde de verdad merece la pena leerlos.

Nunca se muestra el valor de un secreto. De las ocho comprobaciones, solo secret-in-env examina las variables de entorno, y su hallazgo nombra únicamente la clave de la variable; el valor nunca se incorpora al hallazgo, ni se muestra, ni se copia. La comprobación también está pensada para no generar falsos positivos: compara tokens completos delimitados por _ (PASSWORD, PASSWD, PASS, PASSPHRASE, SECRET, TOKEN, APIKEY, CREDENTIAL(S), PRIVATEKEY, y los pares API_KEY, ACCESS_KEY, PRIVATE_KEY, SECRET_KEY, CLIENT_SECRET, AUTH_TOKEN), de modo que COMPASS, PASSENGER_PORT o BYPASS_AUTH no se reportan. Las claves que solo referencian una credencial quedan exentas (_FILE, _PATH, _URL, _URI, _NAME, _ID, _TYPE, _ENABLED, _REQUIRED, _LENGTH, _TIMEOUT, _TTL, _EXPIRY, _ALGORITHM), igual que los valores que claramente no son una credencial: una ruta absoluta, un booleano o un número.

El overlay lista todos los servicios marcados («N of M service(s) flagged · 8 checks»), agrupados por servicio, cada hallazgo en su propia línea con un punto que indica la severidad — ● high, ● medium, ● low — un título corto y una explicación de una línea. Los hallazgos se ordenan del más grave al menos grave. Una vez que un servicio está marcado por algo que requiere acción, también se listan sus hallazgos informativos de nivel low. Si el servicio bajo el cursor está entre ellos, aparece ya resaltado y la vista se desplaza hasta él. Cuando no hay nada marcado, el overlay lo dice explícitamente y enumera todas las comprobaciones que se ejecutaron («Checked: Docker socket mounted in, added Linux capabilities, host network, seccomp / AppArmor disabled, container user, secrets in environment variables, missing resource limits, unpinned image.»), de modo que el «todo en orden» también te dice qué cubre realmente; si la lista de servicios aún no se ha cargado, indica que todavía no se ha analizado nada en lugar de dar un falso «todo en orden». j/k desplazan la vista; Esc (o q, o ! de nuevo) lo cierra.

El análisis es un registro extensible de analizadores, no una lista fija: una comprobación nueva aparece automáticamente tanto en el marcador del árbol como en el overlay. El propio texto del overlay también sale de ese registro: el número de comprobaciones de su cabecera y la lista «Checked:» se generan a partir de los propios analizadores, así que no pueden desfasarse respecto a lo que realmente se ejecutó, como sí le pasaría a una lista fija en el código. La tecla se puede reasignar como security_risks en keys.yaml.

Ambas provienen del manager de swarm. El overlay se abre en un resumen en tabla pensado para el operador, con las secciones ordenadas por relevancia operativa — redes, etiquetas, volúmenes/montajes y secretos (y configs) primero, luego puertos, imagen, modo, env, recursos, colocación y política de actualización (más estado, nodo e id de contenedor para un contenedor/tarea), con los ids y las marcas de tiempo al final. La primera línea del overlay, dentro del borde y fija por encima del contenido que se desplaza, es una barra de pestañas con sus tres vistas — table 1   stats 2   raw json 3 — con la actual en el color de realce; tiene la misma forma que la barra de pestañas de la ventana principal: una etiqueta seguida del dígito que la selecciona. 1, 2 y 3 saltan directamente a la tabla, a stats y al JSON en bruto del daemon, y t sigue alternando tabla → stats → JSON en bruto y vuelta a empezar. La indicación del pie es simplemente 1-3/t view, y el título del borde ya no repite el nombre de la vista actual — dice solo inspect service foo, porque la barra ya indica dónde estás. Ten en cuenta que la vista en tabla es la vista de la tarea que tiene el manager, no un docker container inspect completo y local del contenedor en ejecución — está previsto añadir una inspección real del contenedor a través del agente.

La vista de stats. La segunda de las tres es el uso de recursos en vivo — las mismas lecturas que alimentan los marcadores del árbol, así que abrirla no supone ninguna llamada extra y las cifras se siguen actualizando mientras está abierta. Es una tabla, con una fila por contenedor del servicio (o con el único contenedor, en la inspección de una tarea):

RESOURCE USAGE measured on each node, refreshed with the tree CONTAINER NODE HEALTH CPU MEMORY gl_gitlab.1 docker3v2 healthy 0.07 / 4.00 cores (2%) 6.823GiB / 8GiB (85%) limits are the container's own where it has one, otherwise the node's capacity

Una tabla, porque un porcentaje a secas no se entiende si no sabes de antemano cómo mide la herramienta: ¿94% de qué? Cada celda lleva sus propias unidades, así que 0.07 / 4.00 cores no necesita leyenda y el porcentaje queda junto a la cifra de la que es porcentaje; y varias réplicas se comparan recorriendo una columna en lugar de cotejar bloques apilados. La columna HEALTH expresa el veredicto con palabras: healthy, unhealthy, starting o none para un contenedor que no declara ningún healthcheck. none y healthy son deliberadamente palabras distintas, en lugar de una palabra y un hueco: no hay healthcheck configurado y la sonda se supera son hechos distintos, y un hueco se interpretaría como lo segundo. Un contenedor del que ningún agente ha informado —nodo inaccesible, un agente demasiado antiguo para el RPC Stats, o uno arrancado después de la última lectura— muestra no reading en las dos columnas de recursos en lugar de un cero, que se interpretaría como inactivo.

Los últimos minutos. Bajo la tabla, cada contenedor tiene dos sparklines, de CPU y de memoria, con las últimas lecturas — así distingues un servicio que se mantiene en el 90% de uno que acaba de dispararse al 90%. Ambas usan una escala fija de 0–100% sobre el mismo denominador que la tabla, para que las líneas de dos contenedores sean comparables y la de uno inactivo quede plana. El historial solo se guarda en memoria, como mucho 15 minutos, y las lecturas siguen llegando mientras la vista está abierta. Un hueco es un tramo sin lecturas — un nodo que no respondió, un clúster que no estabas mirando —, nunca una caída a cero.

La nota bajo la tabla indica el denominador: el límite propio del contenedor si lo tiene y, si no, la capacidad del nodo. Eso es lo que da sentido a un porcentaje — el 85% de un límite de 8 GiB y el 85% de un nodo de 64 GiB son cosas muy distintas. La memoria se muestra en unidades binarias (MiB/GiB), las mismas que usa el detalle de nodo y las mismas que informa el propio docker, así que una misma cifra nunca se lee distinta en dos sitios. Con más de un contenedor medido, la vista añade un resumen bajo la tabla: CPU y memoria de la peor réplica —no la media, que esconde precisamente el contenedor a punto de caer por OOM— más la memoria total de todas ellas. En consecuencia, la entrada t del overlay de ayuda ? dice cycle table / stats / raw JSON.

La sección NETWORKS es desplegable y responde a «¿en qué dirección se llega a esto?» antes de expandir nada: cada red conectada se muestra como una fila contraída + <network> 🔒 vip 10.0.5.2/24 (2 dns names). Un icono de candado 🔒 tras el nombre de la red marca una red overlay cifrada (cifrado del plano de datos, --opt encrypted); si no aparece, la red no está cifrada. En la inspección de un servicio, la dirección se marca como vip — la IP virtual del servicio en esa red, la dirección en la que responde el balanceador de carga del swarm, tomada del ServiceInspect del manager (Endpoint.VirtualIPs). En la de un contenedor/tarea, se marca como addr: la dirección propia de ese contenedor en esa red. Un servicio en modo de endpoint dnsrr no tiene ninguna VIP — es así por diseño, no es un dato que falte —, así que, en lugar de un hueco, la red expandida muestra la línea no vip — dnsrr endpoint mode, the DNS name resolves to the containers. La red ingress también aparece aquí, aunque ninguna spec la mencione: el swarm conecta el servicio a ella por su cuenta (ver más abajo). Se añade después de las redes que declara la spec, nunca intercalada entre ellas, y su cabecera es + ingress vip 10.0.0.250/24 (routing mesh): la nota (routing mesh) sustituye a un recuento de nombres DNS que siempre diría (0 dns names).

Sitúate sobre una fila de red y pulsa Enter para expandirla o contraerla. Expandida, lista los nombres DNS que resuelven al servicio/contenedor en esa red — el nombre del servicio, tasks.<service> y cualquier alias personalizado —, para que veas, red por red, con qué nombre DNS se llega a él y qué alias tiene. Debajo hay una segunda fila desplegable, + 2 containers (en singular, + 1 container), y Enter sobre esa abre el nivel más profundo: una fila por contenedor, alineada en columnas, web.1 10.0.1.5/24 host-a — nombre de la tarea, su dirección en esta red y el nodo en el que se ejecuta (las tareas replicadas se llaman <service>.<slot>; las globales, que no tienen slot, <service>.<node>).

Lo que se lista se filtra por el estado deseado de la tarea, no por el actual: aparece toda tarea que el manager sigue queriendo en ejecución, incluidas las que solo están en preparing, assigned o starting — ya tienen su dirección, y durante una actualización progresiva son la mayoría, así que filtrar por el estado actual vaciaría el desglose justo cuando más interesa. Una tarea que el manager ha dado por perdida — estado deseado shutdown, es decir, sustituida por una actualización progresiva, eliminada al reducir la escala o fallida — no se lista: su dirección ya se ha liberado y puede pertenecer a otro contenedor, así que mostrarla sería directamente erróneo. Una tarea que todavía no sirve tráfico lleva su estado entre paréntesis al final de la fila, web.1 10.0.1.5/24 host-a (starting); una en ejecución no lleva sufijo. Las filas proceden de un TaskList de la API del manager filtrado por el servicio y se obtienen en la medida de lo posible: un error de la API simplemente deja el desglose vacío. Los dos niveles se contraen de forma independiente; contraer la red oculta también el nivel de contenedores.

La fila de ingress es la que no figura en ninguna spec. Swarm conecta el servicio a la red ingress por su cuenta en cuanto este publica un puerto en modo ingress, y esa conexión no aparece en ninguna parte de la spec del servicio — pero su vip es la dirección en la que responde realmente la malla de enrutamiento (routing mesh), que es lo primero que quieres saber cuando un puerto publicado no se comporta como debe. Por eso tiene una fila propia, añadida después de las redes que declara la spec y con una forma algo distinta. En ingress no resuelve ningún nombre DNS del servicio, así que, donde otra red cuenta sus nombres, esta cabecera lleva la nota (routing mesh); expandida, la fila lista en su lugar los puertos publicados por ingress que han llevado allí al servicio — la razón de ser de la fila —, uno por línea: published 2222 -> 22/tcp. Los puertos publicados en modo host no pasan por la malla de enrutamiento y, deliberadamente, no se listan ahí. Por debajo, el desglose llega hasta los contenedores igual que en cualquier otra fila de red: el mismo nivel + 1 container, con la dirección propia de cada contenedor en la red ingress. Un servicio que no publica ningún puerto por ingress no tiene VIP en ella — y, por tanto, tampoco esa fila.

Un servicio GitLab que publica SSH en 2222, con ambos niveles expandidos:

- dbnet vip 10.0.1.137/24 (2 dns names) gl_gitlab tasks.gl_gitlab - 1 container gl_gitlab.1 10.0.1.54/24 docker3v2 - ingress vip 10.0.0.250/24 (routing mesh) published 2222 -> 22/tcp - 1 container gl_gitlab.1 10.0.0.64/24 docker3v2

Copiar dentro de NETWORKS devuelve la dirección sin su máscara — 10.0.5.2, tal como la pegarías en un curl o un ping: en una fila de red, su vip/addr; en una fila de contenedor, la dirección de ese contenedor. Una fila de red sin dirección (dnsrr) copia el nombre de la red, como antes. En los dos tipos de fila desplegable, Enter expande o contrae; en cualquier otra línea, copia (y y siempre copia).

Empieza por a: el menú de acciones. En la inspección de un servicio (solo ahí), a abre una única lista con todos los editores y acciones que ofrece el overlay, para que no tengas que recordar ~14 teclas que distinguen mayúsculas y minúsculas (d/D, s/f, p/l/e, n/S/v, r/P, R, X). Las entradas, en orden: update image version… (set image version… cuando no se encontró una más nueva — fijar un tag a tu elección o volver a uno anterior es igual de válido), diff spec (previous → current), roll back to the previous version, placement diagnosis — why a task is missing, scale, force-update, edit ports, edit labels, edit env, edit networks, edit secrets, edit mounts, edit resources, edit placement, remove service — la destructiva, marcada en rojo — y Cancel. Te desplazas con j/k (g/G saltan a la primera/última entrada) y Enter selecciona; Esc, o la entrada Cancel, cierra el menú sin hacer nada. Recursos reservados. Los detalles del nodo incluyen un bloque reserved by tasks (scheduler's view): para CPU y memoria, una barra junto con reserved / capacity y cuánto queda libre. La barra es verde, pasa a amarillo a partir del 75% y a rojo al llegar al 100% o superarlo; la sobrerreserva se indica expresamente y el valor libre nunca es negativo. Un nodo que no informa de su capacidad lo indica en lugar de dibujar una barra. El bloque no supone ninguna llamada adicional a la API — la lista de nodos ya obtiene la lista de tareas.

Son reservas, no uso. Las cifras son la suma de las Reservations declaradas por las tareas — exactamente el cálculo que hace el propio planificador de swarm al decidir si una tarea cabe en un nodo, y el motivo habitual de que un servicio no se pueda programar. El consumo real de CPU/RAM es local a cada nodo y no es lo que se muestra aquí: tiene su propio bloque, justo debajo. Las tareas que no declaran ninguna reserva se cuentan y se indican por separado: aquí no reservan nada, pero pueden consumir el nodo entero, así que un porcentaje bajo no significa que el nodo esté inactivo — y en la mayoría de los clústeres muy pocos servicios definen reservas. Una tarea mantiene su reserva desde el momento en que se le asigna un nodo hasta que llega a un estado final: por tanto, las tareas en preparing o starting cuentan, y las que están en shutdown / failed / complete / rejected no (el swarm las conserva en la lista de tareas como historial).

En uso por los contenedores. Debajo hay un segundo bloque — in use by containers (measured on the node) — dibujado con las mismas barras proporcionales: lo que los contenedores del nodo están usando realmente en este momento, CPU en núcleos y memoria, cada uno respecto a la capacidad del propio nodo. Los dos bloques se mantienen separados a propósito, porque responden a preguntas distintas y sus valores suelen estar muy alejados: un nodo puede estar totalmente reservado y sin carga, o apenas reservado y al límite. Las cifras proceden del agente de ese nodo, la misma fuente que los marcadores de uso del árbol de servicios — mientras el delta de CPU no está listo, la línea dice measuring…, y un nodo cuyo agente sea inaccesible o demasiado antiguo no muestra ningún bloque, en lugar de una fila de ceros que se interpretaría como «inactivo».

Solo contenedores. Aquí se cuentan los contenedores del nodo — el kernel, el daemon de docker y cualquier cosa que se ejecute fuera de docker no entran en la cifra. No es la carga media (load average) del nodo, y el propio bloque lo indica.

Imágenes en este nodo. Al final de los detalles aparece un bloque images on this node: cuánto ocupa el almacén de capas del nodo y en cuántas imágenes, y cuánto de eso se puede liberar en restos sin tag (un nodo sin nada sin tag lo indica, en lugar de mostrar un cero). Si hay restos, una línea más indica cuánto hay además con tag pero sin usar — planteado como un coste, eliminarlo implica volver a descargar esas imágenes, no como una oferta. El bloque existe porque las imágenes son el único recurso local del nodo que desde el lado del clúster no se ve en absoluto: la API del manager no sabe nada de las imágenes, a diferencia de los volúmenes, de los que al menos sabe que están montados. Los volúmenes ya se podían gestionar desde swarmexec en todo el clúster; un nodo cuyo disco se iba llenando poco a poco de capas antiguas ni siquiera se veía. No interpretes la segunda entrada como «lo mismo, pero más». «Every unused image» elimina imágenes que pertenecen a algo que simplemente no se está ejecutando en este instante: un servicio escalado a cero, una tarea que se está reiniciando, un stack que paraste ayer. Todos pierden su imagen y tienen que volver a descargarla para volver a arrancar, y si el registro no es accesible, no volverán a levantarse. Cada una de las dos entradas pasa por su propio diálogo de confirmación, que expone exactamente esa consecuencia e indica los bytes que liberaría; son textos separados precisamente para que ninguno acabe describiendo, por error, lo que hace el otro.

Dos modos, dos permisos. El agente los autoriza como dos acciones distintas — image.prune para los restos sin tag e image.prune.all para la limpieza completa —, de modo que una política puede permitir liberar capas sin tag sin permitir la operación destructiva. Cada prune se registra en el log de auditoría del agente, con el modo usado, el espacio liberado y el número de imágenes eliminadas.

De dónde salen las cifras. Se leen de la misma fuente que usa docker system df, y coinciden exactamente con él — comprobado en un nodo real con 56 imágenes, 32,70 GB en disco y 22,99 GB liberables. En concreto, swarmexec no suma los tamaños de las imágenes una a una: el tamaño de una imagen incluye todas las capas que la forman, y las capas se comparten, así que esa suma infla mucho el resultado — durante el desarrollo indicaba 32,7 GB donde el daemon decía 22,2 GB. Una salvedad que conviene mencionar: la cifra de solo sin tag es una cota inferior — una capa compartida por dos imágenes sin tag no cuenta en el tamaño exclusivo de ninguna de las dos —, así que un prune de las imágenes sin tag puede liberar algo más de lo anunciado, nunca menos.

Tiene el mismo requisito que las cifras de uso y de salud de más arriba: necesita agentes de esta versión o posteriores. Un nodo con un agente más antiguo simplemente no muestra el bloque de imágenes, e indica que no respondió si pulsas P — actualiza los agentes con swarmexec init --force.

Pestaña Configs

Pestaña 7 — la equivalente de la pestaña Secrets para el otro tipo de objeto que el swarm entrega a los contenedores, con una diferencia decisiva: el contenido de un config sí se puede leer. La pestaña Secrets nunca puede mostrar un valor (la API de Docker no lo devuelve); el detalle de un config muestra el contenido real, así que ves lo que recibe de verdad un servicio sin tener que recurrir a docker config inspect. Esa es la razón de ser de esta pestaña.

La lista es de solo lectura: CONFIG (nombre), USED BY (cuántos servicios lo montan), SIZE, AGE, UPDATED y LABELS (número de etiquetas).

TeclaAcción
Enter / iabre el overlay de detalle: nombre, id, tamaño, fecha de creación, fecha de actualización, los servicios que lo montan, sus etiquetas — y el contenido del config
j k / g Gen el overlay de detalle: desplazarse · ir al principio / al final (Esc cierra)

El contenido se obtiene bajo demanda, al abrir el overlay — no junto con la lista —, porque un config puede ser un nginx.conf entero; hasta que llega, el overlay muestra loading…, y un config vacío indica (empty). Lo que ves es una vista previa, limitada a la vez a 64 KiB y a 500 líneas. Hacen falta los dos límites: limitar solo los bytes sigue permitiendo que un archivo de líneas muy cortas se convierta en decenas de miles de filas en pantalla —cada una con su sangría—, que es lo que de verdad hace que la vista vaya lenta. El truncado siempre se indica («… truncated at 500 lines», o en el límite de bytes), nunca es un corte silencioso, y el contenido binario se señala, no se vuelca («(binary content, N — not shown)», que se determina buscando bytes NUL al principio de los datos). El config completo está a un docker config inspect de distancia.

USED BY se calcula exactamente igual que en la pestaña Secrets: el swarm no mantiene ningún índice inverso que vaya de un config a los servicios que lo usan, así que swarmexec lee las specs de los servicios (un único ServiceList) y reconoce una referencia por ID o por nombre del config — una spec puede usar cualquiera de las dos formas, así que se buscan ambas y se combinan los resultados. Se hace en la medida de lo posible: si no se puede leer la lista de servicios, los configs se muestran igual, solo que sin esa relación.

En una shell integrada, Ctrl-] te desconecta (sin terminar el proceso). La vista de logs — de un único contenedor o los logs agregados de un servicio — admite el mismo análisis y filtrado según el formato que el comando logs:

La vista vuelve a mostrar al momento las líneas del buffer cuando cambias el formato, el nivel o el grep, y la barra de título muestra el estado activo fmt:… lvl:… grep:….

En modo seguimiento, la vista de logs se reconecta cuando se reemplaza un contenedor, igual que el comando logs — tanto en los logs de un único contenedor como en los logs agregados de un servicio (cada réplica se sigue por su slot). Los avisos de reconexión aparecen intercalados en la vista de logs.

Visor de logs

Pulsa ` (acento grave) desde cualquier pestaña para abrir o cerrar un overlay de logs en vivo. Muestra las entradas más recientes del buffer circular en memoria — las más nuevas abajo —, se actualiza mientras está abierto y usa un color para cada nivel (rojo = error, amarillo = warn, gris = debug). ↑/↓ desplazan la vista; Esc, q o ` lo cierran. Es la ventana de la TUI a los mismos logs que se escriben en el archivo de log, ya que la propia terminal no puede mostrarlos mientras la UI está dibujando.

Capacidad de respuesta. La lista de contenedores se refresca fuera del hilo de la UI (antes, sus dos llamadas a la API del manager se ejecutaban en ese hilo y podían bloquear brevemente la TUI), y un watchdog en segundo plano registra un aviso cuando el bucle de eventos se atasca — útil para diagnosticar lentitud desde el visor de logs.

Teclas personalizadas

Las teclas de acceso directo se pueden reasignar en ~/.config/swarmexec/keys.yaml (junto a config.yaml; cambia la ruta con $SWARMEXEC_KEYS). Cada valor es una única tecla, o la palabra space. Las teclas estructurales — Enter, Esc, Tab, las flechas, las teclas numéricas de las pestañas 1–9 y los alias de vim j/k/g/G — son fijas. El pie siempre muestra las teclas que tienes configuradas, y el overlay ? las lista todas.

# ~/.config/swarmexec/keys.yaml — omite una línea para conservar su valor por defecto quit: q refresh: r copy: y toggle_mouse: m search: / fold: h unfold: l forward: p container_inspect: i logs: L security_risks: "!" # "!" debe ir entre comillas — YAML stack_group: s volume_select: space volume_select_all: a volume_delete: d volume_prune: P volume_used_by: i volume_attach: A volume_sort: s volume_sort_reverse: S volume_new: n network_attached: i network_new: n context_use: u context_new: n context_delete: d node_edit_labels: l node_availability: a node_prune_images: P secret_delete: d secret_new: n forward_stop: d forward_copy_url: o

La carga nunca falla: una tecla no válida o reservada, una acción desconocida o dos acciones asignadas a la misma tecla en una pestaña vuelven, cada una, a su valor por defecto, y la UI muestra los avisos una vez al arrancar.

quit y copy también funcionan dentro de todos los diálogos — el overlay de inspección, las vistas de detalle, el visor de logs —, así que una tecla reasignada también cierra y copia allí. Por la misma razón, no pueden usar una tecla que un diálogo ya utiliza para sí mismo, como t, d o i: en ese caso se mantiene el valor por defecto, con un aviso. El editor de env es la excepción: allí cada letra es un comando de vim o texto, así que se sale con Esc / :q y se copia con yy, sea cual sea la tecla asignada a quit y copy.
